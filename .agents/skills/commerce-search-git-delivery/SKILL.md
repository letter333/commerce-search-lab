# 이슈·PR 관리와 Git 전달

요청한 변경만 올바른 저장소와 브랜치에 전달한다. [작업 지침](../../../AGENTS.md)과 [검증 기준](../../../docs/harness.md)을 따른다. 사용자 지시와 세션에서 이미 받은 권한을 우선하며, 허가된 작업에 반복 승인을 요구하지 않는다.

## 작성 템플릿

실제 메시지와 본문은 아래 템플릿으로 작성하며, 구체적인 명령·주석 제거·GitHub 적용 시점은 [사용법](../../../docs/git-templates.md)을 따른다.

| 용도 | 템플릿 |
|---|---|
| 커밋 메시지 | [.gitmessage.txt](../../../.gitmessage.txt) |
| 작업 이슈 | [task.md](../../../.github/ISSUE_TEMPLATE/task.md) |
| PR 본문 | [pull_request_template.md](../../../.github/pull_request_template.md) |

- 자리표시자를 실제 작업·이슈·검증 결과로 바꾸고 안내 주석을 제거한다. 미실행 결과와 체크박스를 미리 완료로 표시하지 않는다. 비밀값을 본문·메시지·첨부에 넣지 않는다.
- 커밋 편집에는 `git commit --cleanup=strip --template .gitmessage.txt`를 사용한다. `--file`에는 주석과 자리표시자를 제거한 실제 메시지 파일만 전달한다. 이슈를 CLI/API로 작성할 때는 YAML frontmatter를 제외한 본문과 별도 제목을 사용한다.
- 템플릿 작성·수정 요청 자체는 실제 이슈/PR 생성·커밋·푸시·머지나 Git 설정 변경 지시가 아니다. 아래 전달 권한과 검증 절차를 그대로 적용한다.

## 작업·이슈·PR의 대응

- 사용자 규칙은 **작업 시작 전 이슈 등록 → 이슈 하나당 PR 최대 하나 → 해당 PR 머지 후 이슈 종료**다. PR이 아직 없을 수는 있지만 같은 이슈에 두 번째 PR을 만들지 않는다. 여러 커밋이나 리뷰 수정은 같은 PR에 누적한다.
- [상세 구현 계획](../../../docs/implementation-plan.md)의 최종 작업 ID 하나를 이슈 하나와 PR 하나로 연결한다. 같은 결과에 필요한 코드·테스트·문서는 함께 포함한다. 독립 결과로 나눌 필요가 있으면 이슈/PR 생성 전에 작업 ID를 먼저 나눈다. 단계 전체를 묶는 부모/추적 이슈를 여러 구현 PR의 종료 대상으로 사용하지 않는다.
- 한 PR도 하나의 작업 이슈만 해결한다. 다른 선행 이슈는 일반 참조로 연결하며 여러 이슈의 종료 키워드를 넣지 않는다. 머지 이후 새 요구나 결함은 별도 작업 ID·이슈·PR로 처리한다.
- 실제 작업 착수 요청에는 사용자가 정한 이 절차에 따른 해당 이슈의 조회·등록을 포함한다. 커밋·푸시·PR 생성은 요청된 전달 범위와 기존 권한을 따르며, PR 생성이나 푸시만으로 머지까지 허가된 것으로 보지 않는다. 머지는 사용자의 해당 지시가 있을 때 수행하고, 확인된 머지 이후 해당 이슈의 종료는 이 정책에 따라 처리한다.
- 스킬·지침·계획의 작성이나 점검만 요청받은 경우는 그 산출물까지 처리한다. 절차 설명만으로 실제 이슈/PR을 생성하거나 커밋·푸시·머지·이슈 종료를 실행하지 않는다.

## 작업 시작 전 이슈 등록

1. 저장소의 실제 GitHub 대상과 현재 작업 ID·범위·완료 기준을 확인한다. `gh` 또는 사용 가능한 GitHub 도구로 기존 이슈와 모든 상태의 PR을 조회한다. 이슈 번호/링크, 작업 ID, 연결된 PR·타임라인·브랜치를 함께 확인하며 첫 검색 페이지나 열린 PR만 보고 없다고 단정하지 않는다.
2. 같은 작업의 이슈가 있으면 재사용한다. 미완료 작업의 이슈가 닫혀 있으면 사유와 기존 PR부터 확인하고 필요한 재개를 처리한다. 새 이슈를 만들어 기존 PR 이력이나 이슈당 PR 제한을 우회하지 않는다. 목록 조회가 불완전하거나 중복 상태가 불명확하면 새 이슈/PR을 만들지 않는다.
3. 이슈가 없으면 구현 전에 등록한다. 제목은 작업 ID와 결과를 담고, 본문에는 목적·포함/제외 범위·선행 작업·완료 기준·먼저 검증할 사례를 적는다. 예를 들어 M1-01 이슈는 버전 조합과 실행 계약까지만 포함한다. 실제 검증 결과는 수행 후 갱신하고 비밀값은 넣지 않는다.
4. 이슈 URL과 작업 ID를 작업 기록에 연결하고 이슈 전용 작업 브랜치를 사용한다. 새 브랜치는 `codex/issue-123-short-description` 형식을 기본으로 한다. 기존 적절한 브랜치는 재사용하고 사용자 변경을 보존한다. 현재 단위를 담당하는 에이전트 하나만 이슈/PR을 생성하며 다른 에이전트는 그 번호를 공유한다.
5. 인증·네트워크·저장소 정보가 없어 등록할 수 없으면 이슈 초안과 독립적인 조사를 준비하고 제약을 기록한다. 이슈가 등록됐다고 표시하거나 이슈 없이 실제 구현을 시작하지 않는다. 이미 받은 권한을 재확인하지 말고 실제로 부족한 정보나 접근만 해결한다.

## 하나의 PR로 전달

1. PR 생성 직전에 이슈와 브랜치의 기존 PR을 다시 확인한다. 열린 PR이나 draft가 있으면 그 PR을 갱신한다. 머지 없이 닫힌 PR은 같은 PR의 재개 가능성을 확인하며 대체 PR을 새로 만들지 않는다. 재개할 수 없거나 PR이 이미 여러 개면 임의 삭제/종료/새 이슈로 우회하지 말고 충돌 상태를 보고한다. 이미 머지된 PR이면 이슈 종료 상태를 정리한다.
2. 아래 커밋·푸시 검증을 마치고 전달 권한이 있는 범위에서만 브랜치를 푸시하고 PR 하나를 만든다. 생성 요청의 응답이 끊기면 서버 상태를 조회해 성공 여부를 확인한 뒤 재시도한다. 동일 작업의 생성 요청을 병렬 실행하지 않는다.
3. PR의 실제 base/head 저장소·브랜치와 diff가 해당 이슈 범위인지 확인한다. 본문에는 변경된 동작·검증 명령과 실제 결과·남은 제약을 쓰고 해당 이슈의 `Closes #123`을 넣는다. 번호는 실제 이슈 번호로 바꾼다. 같은 작업의 후속 커밋·리뷰 수정은 동일 브랜치/PR에 반영한다.
4. 이슈·PR의 여러 줄 본문은 구조화된 도구 인수 또는 UTF-8 임시 파일과 `--body-file`로 전달한다. 작업 기록에 이슈 URL·PR URL·base/head·구현/검증 상태를 남긴다. **구현·검증 완료와 PR 머지·이슈 종료 완료를 별도 상태로 기록한다.**

## 머지 확인 후 이슈 종료

- PR 생성·승인·자동 머지 예약·머지 대기열 진입·머지 없이 close된 상태는 실제 머지가 아니다. 실제 PR의 merged 상태, 머지 시각/커밋과 대상 브랜치를 확인한 뒤에만 이슈 종료를 처리한다. 머지 없이 닫힌 PR의 이슈는 미해결로 유지한다.
- 기본 브랜치를 대상으로 하는 PR의 종료 키워드는 자동 종료에 사용할 수 있다. 비기본 브랜치에서는 키워드가 해석되지 않으므로 본문/작업 기록의 이슈 연결을 유지하고 머지 후 직접 상태를 확인한다. [GitHub 이슈 연결 문서](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)
- 저장소의 자동 종료 설정이 비활성일 수도 있다. 머지 후 해당 이슈가 열려 있으면 실제 연결과 완료 기준을 확인하고 `completed` 사유로 닫은 뒤 상태를 다시 조회한다. 자동 종료를 위해 저장소 설정을 임의로 바꾸지 않는다. [GitHub 자동 종료 설정 문서](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/managing-auto-closing-issues)
- 이미 닫힌 이슈는 중복 종료하지 않는다. 이슈 종료 권한·네트워크 문제나 완료 기준 누락은 `PR 머지됨 / 이슈 종료 미완료`로 기록하며 성공으로 보고하지 않는다. 상태 변경 재시도 전 서버 상태를 확인한다.
- 인계 시 작업 ID·이슈/PR URL·머지 상태와 SHA·이슈 종료 상태를 남긴다. 실제 PR 조회 없이 로컬 브랜치나 커밋 메시지만으로 머지/종료를 단정하지 않는다.

## 요청 범위와 초기 상태

- 점검 요청은 점검까지만 수행한다. 커밋은 로컬 이력 변경이고 푸시는 원격 변경이다. 커밋 요청을 푸시 요청으로 확대하지 않는다. 둘 다 요청했다면 준비·검증 후 연속 수행한다.
- `git status --short --branch`, 현재 브랜치, `git diff --stat`, `git diff --cached --stat`로 작업 전 상태를 확인한다. 기존 staged 파일과 동일 파일의 unstaged 변경을 구분한다. 새 파일은 diff에 나타나지 않으므로 따로 검토한다.
- 요청과 무관한 staged 변경을 함께 커밋하거나 임의로 unstage·stash·reset하지 않는다. 의도한 변경만 담는 방법을 확인하고, 부분 staging이 필요하면 해당 hunk를 검토한다. 안전하게 분리할 수 없으면 나머지 점검을 끝내고 포함 범위만 확인한다.
- detached HEAD나 대상이 불분명한 브랜치에서 추측해 진행하지 않는다. 새 브랜치가 필요하면 기본 `codex/` 접두사를 사용하되 사용자 선택을 따른다.
- 소유권 경고는 저장소 경로·소유자를 확인하고 필요한 경우 해당 명령에만 `-c safe.directory=<확인한 경로>`를 적용한다. 편의를 위해 전역 설정이나 `safe.directory=*`를 추가하지 않는다.

## 커밋 메시지와 단위

사용자가 선택한 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)을 따른다. 아래 타입 목록·한국어 요약·이슈 참조·검증 기준은 이 프로젝트의 작성 규칙이다. 앞으로 작성하는 작업 커밋에 적용하며, 규칙 도입만을 이유로 과거 이력을 고치지 않는다.

### 메시지 형식

- 제목은 `type(scope): 한국어 요약`으로 작성한다. type과 scope는 소문자 영문을 사용한다. scope는 변경 영역이 분명하면 넣고, 저장소 전반의 변경처럼 적절한 단일 영역이 없으면 `type: 한국어 요약`으로 생략할 수 있다.
- scope는 `catalog`, `index`, `search`, `query`, `ranking`, `api`, `ui`, `eval`, `seeds`, `build`, `skills` 등 실제 변경 영역을 사용한다. 이슈 번호나 임의의 작업 단계명을 scope로 대신하지 않는다.
- 요약은 한 줄로 무엇이 달라졌는지 구체적으로 적는다. `수정`, `작업 완료`, `WIP`, `update`처럼 결과를 알 수 없는 제목은 쓰지 않는다. 파일 목록이나 수행하지 않은 품질/성능 성과를 제목으로 삼지 않는다.
- 본문이 필요하면 제목 뒤 빈 줄을 두고 변경 이유·동작 차이·중요한 제약과 실제 검증 근거를 적는다. 짧은 변경에 불필요한 본문을 강제하지 않으며, 상세 Red/Green 기록은 작업 기록에 연결할 수 있다.
- 마지막에는 빈 줄을 두고 해당 작업의 **실제 이슈 하나**를 `Refs #번호`로 참조한다. 작업 ID는 필요하면 본문에 함께 적되 이슈 번호를 대신하지 않는다. 이슈가 없으면 앞의 이슈 등록 절차를 따르며 번호를 만들어 넣지 않는다.
- 커밋 메시지에서는 `Closes`, `Fixes`, `Resolves` 같은 이슈 종료 키워드를 사용하지 않는다. 종료 연결은 해당 PR 본문에 두고 실제 머지 후 이슈 종료를 확인한다. 커밋에는 일반 참조인 `Refs`를 사용한다.

| type | 사용하는 변경 |
|---|---|
| `feat` | 새로운 검색/API/도구 기능이나 사용자 동작 추가 |
| `fix` | 기존 계약과 다른 동작 또는 버그 수정 |
| `docs` | 문서·계획·스킬 지침 변경 |
| `test` | 제품 동작 변경 없이 테스트·fixture 보강 |
| `refactor` | 외부 동작을 유지하는 내부 구조 개선 |
| `perf` | 측정 근거가 있는 성능 개선 |
| `build` | Gradle·의존성·패키징·실행 이미지 구성 |
| `ci` | CI 워크플로와 검사 실행 구성 |
| `style` | 동작을 바꾸지 않는 코드 서식 변경. UI 기능/표현 변경을 뜻하지 않음 |
| `chore` | 위 분류에 속하지 않는 저장소 유지관리·개발 시드 데이터 변경 |
| `revert` | 기존 변경 되돌리기. 본문에 대상 SHA와 이유 기록 |

타입은 파일 확장자나 테스트 포함 여부가 아니라 **커밋의 주된 결과**로 고른다. 기능과 그 기능의 테스트를 함께 추가하면 `feat`, 버그 수정과 재현 테스트를 함께 추가하면 `fix`다. 독립적인 목적이 섞였으면 각각 검증 가능한 커밋으로 나눈다. 이슈 범위를 넘는 별도 결과는 별도 작업 이슈로 분리한다.

기존 API·설정·데이터 계약의 호환성을 깨면 `feat(api)!: ...`처럼 `!`를 붙이고, 이 프로젝트에서는 `BREAKING CHANGE: ...` 후터도 함께 작성해 깨지는 계약과 전환 방법을 설명한다. 이 둘을 함께 쓰는 것은 프로젝트 규칙이며, 표준 자체가 둘 모두를 필수로 요구한다는 뜻은 아니다. 단순 내부 리팩터링이나 변경량이 많다는 이유로 표시하지 않는다. 표기만으로 호환성 변경 범위나 릴리스/버전 변경이 허가되는 것은 아니다.

아래는 형식 예시이며 실제 이슈·구현·검증 결과가 아니다. 사용할 때는 실제 번호와 확인한 내용으로 작성한다.

```text
fix(search): 가격 상한과 같은 상품을 검색 결과에 포함

M1-20의 가격 경계 계약에 맞춰 상한 비교를 수정한다.
경계 테스트와 check 결과는 해당 작업 기록에 연결한다.

Refs #123
```

### 커밋을 나누는 기준과 이력

- **한 커밋은 검증 가능한 목적 하나**를 담는다. 필요한 코드·테스트·계약·문서는 함께 묶고 파일별로 기계적으로 쪼개지 않는다. 이슈/PR 하나에 여러 작은 커밋을 허용하며, PR 개수와 커밋 개수를 같게 맞추지 않는다.
- 일반 전달 커밋은 해당 변경의 검증을 마친 상태로 만든다. 동작 변경은 테스트 선행 Red→Green을 수행하되 Red를 증명하려고 실패 상태를 커밋/푸시하지 않는다. 이미 통과하는 보호 테스트만 추가한 커밋은 검증 근거가 있으면 가능하다. 아래의 변경 종류별 완료 검증을 유지한다.
- 리뷰 수정은 같은 PR에 후속 커밋으로 반영한다. 메시지 형식을 맞추기 위해 기존 staged 변경을 바꾸거나 다른 작업을 섞지 않는다. `amend`, rebase, squash 등 이력 재작성과 강제 푸시는 단순 커밋/푸시 요청에서 권한을 추정하지 않고, 해당 작업에 이미 받은 지시와 범위가 있는지 확인한다.
- PR 제목도 같은 형식을 권장한다. 머지 방식은 별도 사용자 지시와 저장소 정책을 따르며, squash가 선택된 경우 최종 메시지도 해당 작업과 이슈를 정확히 설명하도록 확인한다. PR 본문의 종료 키워드가 자동 생성된 squash 메시지에 복사되면 커밋의 이슈 참조는 `Refs`로 정리하고 종료 키워드는 PR 본문에 유지한다. 이 규칙만으로 자동 버전 증가·릴리스·commitlint·Git hook을 추가하지 않는다.
- 여러 줄 커밋 메시지는 UTF-8 파일과 `git commit --file <메시지 파일>`로 정확히 전달할 수 있다. 메시지 파일은 임시 경로에 두고 stage하지 않으며, 메시지에도 비밀값을 넣지 않는다. 실제 커밋 권한은 아래 검증 절차와 별도로 확인한다.

## 커밋할 내용과 검증

1. 의도한 파일·hunk의 diff를 읽고 삭제·이름 변경·실행 권한·줄바꿈 변경까지 확인한다. 관련 없는 리팩터링과 일괄 포맷 변경을 섞지 않는다.
2. 새 파일과 staged 내용에 `.env`, 자격증명, 토큰, 개인키, 비공개 데이터, 로컬 절대 경로가 포함됐는지 검토한다. 값은 출력·보고서·커밋 메시지에 복사하지 않는다. remote URL도 인증정보를 제거한 형태로만 표시한다. 파일명이나 단순 패턴 검색만으로 비밀정보가 없다고 단정하지 않는다.
3. `build/`, `.gradle/`, IDE 설정과 평가·테스트 산출물이 의도치 않게 포함되지 않았는지 확인한다. `gradle/wrapper/gradle-wrapper.jar`는 저장소의 의도된 예외다. `.gitignore`는 이미 추적 중인 파일을 제외하지 않으므로 staged 목록을 직접 확인한다. 필요한 실제 평가 증거는 하네스의 보존 규칙을 따른다.
4. 코드 변경은 `./gradlew.bat check`, 데이터만 변경하면 우선 `./gradlew.bat verifySeeds`, 문서만 변경하면 링크·명령·설명 일치를 검증한다. Unix에서는 같은 인수로 `./gradlew`를 사용한다. 검증 실패를 기대값 약화로 덮지 않고, 실패·미실행·환경 제약을 [작업 기록](../../../docs/worklog.md)에 구분한다.
5. 커밋까지 허가받았다면 검토한 경로 또는 hunk만 stage한다. `git add .`, `git add -A`, `git commit -a`로 변경 전체를 자동 포함하지 않는다. 기존 사용자 staged 내용을 보존하며 최종 `git diff --cached --stat`, `git diff --cached`, `git diff --cached --check`를 확인한다.
6. 검증한 작업 트리와 실제 index의 내용이 같은지 확인한다. 부분 staging으로 차이가 있으면 작업 트리 테스트 통과를 커밋 검증 통과로 기록하지 않는다. 필요하면 index snapshot을 별도 임시 디렉터리에서 검증하고, 사용자의 작업 트리와 index는 보존한다. `--cached`는 다음 커밋에 포함할 index를 비교한다. [Git diff 문서](https://git-scm.com/docs/git-diff)

커밋 직전에 작성자 이름·이메일과 서명 설정이 의도한 계정인지 확인한다. 인증에 사용한 GitHub 계정과 커밋 작성자는 같다고 가정하지 않는다. 개인 이메일 공개가 의도되지 않았다면 현재 저장소에서 사용할 신원을 확인하고, 전역 설정을 임의로 바꾸지 않는다. 커밋 제목은 실제 포함한 하나의 변경 목적을 설명한다.

검토 후 추가 변경이 생기면 영향을 받는 검사만 다시 실행한다. hooks가 파일을 바꿨다면 새 diff와 검증 상태를 확인한다. 기본적으로 실패한 필수 검증을 숨긴 채 커밋하거나 푸시하지 않는다.

기능 추가·버그 수정·동작 변경은 [TDD 개발 기준](../../../docs/harness.md#tdd-개발-기준)에 따라 테스트 선행, Red의 실패 이유, Green 및 최종 검증 기록을 확인한다. 테스트 파일이 있거나 현재 통과한다는 사실만으로 TDD 순서를 입증하지 않는다. 과거 변경에 Red 기록이 없으면 관찰하지 않은 실행을 사후에 만들어 적지 않는다. Red는 개발 중간 단계이며 일반 전달 대상은 Green과 필수 검증을 마친 변경이다.

## 푸시할 이력과 실제 목적지

푸시 요청이 있을 때 적용한다. 로컬 커밋만 요청받았다면 원격 작업을 추가하지 않는다. 보통 Git CLI로 충분하며 GitHub 연결이나 플러그인 설치를 요구하지 않는다.

1. 실제 push URL, `remote.<name>.push`, 브랜치 upstream·pushRemote, `remote.pushDefault` 등 목적지에 영향을 주는 설정을 읽는다. `origin`이나 upstream이 원하는 대상이라고 가정하지 않는다. fetch URL과 push URL이 다르거나 여러 push URL이 있으면 모든 실제 목적지가 허가 범위인지 확인한다.
2. 저장소 소유자·이름, 원격 브랜치와 계정 권한, 알려진 보호 브랜치·PR 규칙을 확인한다. 토큰을 출력하거나 설정을 바꿔 확인하지 않는다. 보호 규칙이 PR을 요구하면 직접 푸시로 우회하지 않는다. 대상이 불명확하면 영향 없는 준비를 마치고 필요한 정보만 묻는다.
3. 승인된 대상의 최신 원격 상태를 fetch로 확인하고 ahead/behind 및 분기를 검사한다. fetch와 push 대상이 다르면 실제 push 저장소의 ref를 기준으로 삼는다. 새 원격 브랜치는 생성 대상과 존재 여부를 확인한다. 네트워크·인증 실패 시 기존 remote-tracking ref를 최신이라고 주장하지 않는다.
4. 대상에 없는 **모든 전송 예정 커밋**의 목록과 내용을 검토한다. 최종 diff에서 사라진 비밀정보도 이전 커밋에 남아 전송될 수 있다. 최신 커밋만 검사하거나 비밀정보를 지운 후속 커밋만으로 해결됐다고 보지 않는다. 새 브랜치에는 아직 원격에 없는 이력까지 포함한다.
5. 원격과 분기됐거나 예상하지 못한 커밋이 포함돼 있으면 push만 보류한다. 이미 요청받은 통합·충돌 해결은 권한 범위에서 진행하고 검증한다. 단순 푸시 요청을 pull·rebase·amend·사용자 이력 재작성의 허가로 확대하지 않는다. 미요청 범위 변경이나 추가로 허가가 필요한 이력 재작성에 대해서만 해결 선택을 확인하며, 영향 없는 검토와 검증은 마친다.
6. 전송할 commit과 목적지가 확정되면 `git -c push.followTags=false push <확인한 remote> HEAD:refs/heads/<확인한 브랜치>`처럼 대상을 명시한다. `remote.<name>.mirror` 등 다른 refs까지 보내는 설정이 없는지 확인하고, `--force`, `--all`, `--mirror`, `--tags`를 일반 절차에 사용하지 않는다. 선택적으로 `--dry-run`으로 전송 대상을 확인할 수 있지만 네트워크에 접속하며 실제 서버 검사 통과를 보장하지 않는다. [Git push 문서](https://git-scm.com/docs/git-push)

hooks·서명·secret scanning·브랜치 보호에서 차단되면 원인을 해결한다. `--no-verify`, 강제 푸시, 보호 설정 변경은 통상 해결책이 아니다. 사용자에게 특별히 허가받은 예외라도 영향과 필요한 권한을 확인하고 적용 중인 저장소 규칙을 따른다. GitHub push protection은 탐지한 비밀정보의 전송을 차단하므로 그 원인을 확인한다. [GitHub push protection 문서](https://docs.github.com/en/code-security/concepts/secret-security/push-protection) 네트워크 오류 후 재시도 전에는 원격 ref를 확인하여 이미 성공한 작업을 중복 처리하지 않는다.

## 완료 보고

- 커밋은 실제 SHA, 포함 범위, 검증 결과로 보고한다. 커밋 이후 상태를 확인해 사용자 staged·unstaged 변경이 보존됐는지도 확인한다.
- 푸시는 명령 결과와 실제 원격 브랜치의 SHA를 확인하고 저장소·브랜치·커밋을 보고한다. remote-tracking ref만으로 성공을 단정하지 않는다.
- 작업의 이슈/PR URL과 현재 상태를 보고하고, 머지까지 수행했다면 실제 머지 SHA와 이슈 종료 여부를 함께 확인한다.
- 점검만 수행했으면 이슈/PR 생성·커밋·푸시·머지·종료 여부를 구분한다. 차단된 작업, 미실행 검증과 남은 사용자 선택을 완료한 작업과 명확히 나눈다.
