# 작은 단위로 구현하기

한 번의 구현 단위에서 **하나의 관찰 가능한 결과**를 만든다. 기능 추가·버그 수정·동작 변경은 **테스트를 먼저 작성하고 Red → Green → Refactor로 진행한다**. 그 결과에 필요한 코드·테스트·계약·문서는 같은 단위에 포함한다. 파일 수나 줄 수를 임의로 제한해 검증에 필요한 변경을 분리하지 않는다.

## 이번 단위 정하기

[작업 기록](../../../docs/worklog.md)의 현재 단계와 사용자가 요청한 범위를 확인한다. 큰 요청이면 완료 조건을 기준으로 의존 순서를 나누고, 지금 구현할 단위 하나만 활성화한다. 범위가 이미 작으면 불필요한 재계획 없이 해당 단위를 정한다.

실제 작업을 시작하기 전에 [Git 전달 스킬](../commerce-search-git-delivery/SKILL.md)로 해당 작업 ID의 이슈를 조회·등록하고 기존 PR을 확인한다. 작업 ID 하나·이슈 하나·PR 최대 하나를 연결하며, PR 머지 후 이슈 종료를 확인한다. 스킬·지침·계획 작성만 요청된 경우에는 원격 작업을 실행하지 않는다는 범위 규칙도 그 스킬을 따른다.

착수 전에 다음 세 가지를 짧게 알린다. 기존 작업 기록이 충분하면 별도 계획 파일은 만들지 않는다.

- **이번 결과:** 사용자가 확인할 수 있는 동작 또는 준비물 한 가지.
- **먼저 작성할 테스트:** 기대 동작, 현재 실패해야 하는 이유, 실행할 명령.
- **후속 항목:** 요청에 포함되지만 다음 단위에서 처리할 작업. 요청 밖의 아이디어는 필요할 때만 기록한다.

예를 들어 M1 전체 요청은 실행 환경 고정 → 카탈로그 검증·로딩 → 분석기·매핑 → Bulk 적재 → baseline·필터 API → 실제 baseline 평가 순으로 진행한다. 환경 고정 단위에서 UI나 오타 교정을 함께 구현하지 않는다. 현재 요청이 환경 고정까지만이면 그 범위에서 완료한다.

## 테스트부터 한 동작씩

1. **Red:** 요구사항이나 재현한 버그를 드러내는 가장 작은 동작 테스트를 먼저 작성하고 실행한다. 예상한 기능 부재·잘못된 동작 때문에 실패하는지 확인한다. 이미 그 실패를 재현하는 테스트가 있으면 먼저 실행해 재사용한다. 처음부터 통과하면 기존 구현이 요구를 충족하는지 확인한다. 충족하면 불필요한 구현을 추가하지 않으며 고의로 기대값을 틀리게 만들어 실패시키지 않는다.
2. **Green:** 확인한 실패를 통과시키는 최소 구현만 추가하고 같은 테스트를 실행한다. 여러 기능의 구현을 먼저 만든 뒤 테스트를 붙이지 않는다.
3. **Refactor:** 통과 상태에서 필요한 구조 개선만 수행하고 영향받는 테스트를 재실행한다. 다음 동작은 새로운 Red부터 시작한다. 한 작업 단위가 끝나면 프로젝트 완료 게이트를 실행한다.

환경 오류·잘못된 테스트 설정·실행되지 않은 테스트는 Red 증거가 아니다. 새 타입이 필요하면 테스트 작성 후 실행에 필요한 최소 선언만 추가하고, 기능 구현에 앞서 동작 실패를 확인한다. 실행 환경이 막혀 있으면 제약을 기록하고 해결 가능한 준비를 진행하되 테스트 선행 개발이 검증됐다고 표시하지 않는다.

상세 적용 범위와 명령은 [하네스의 TDD 기준](../../../docs/harness.md#tdd-개발-기준)을 따른다. 순수 리팩터링은 기존 동작 테스트의 통과 상태를 먼저 확인하며 부족한 동작 검증을 보강한다. 문서·스킬·단순 데이터 수정에 형식적인 실패 테스트를 만들지 않는다.

## 범위가 커질 때

- 현재 결과에 필수인 오류 처리·테스트·계약 수정은 같은 단위에 포함한다. 별도 사용자 기능, 도구 도입, 의존성 업그레이드, 주변 리팩터링은 필요성이 입증되지 않으면 후속으로 남긴다.
- 새 선행 조건을 발견하면 이번 결과에 필요한 최소한의 선행 작업으로 순서를 조정하고 이유를 알린다. 구현도 검증도 안 된 여러 기능을 동시에 쌓지 않는다.
- 서브에이전트는 현재 단위의 독립적인 조사·구현·검증·리뷰에 한정한다. 동작 테스트를 작성하는 동안 다른 에이전트가 그 동작의 구현을 먼저 시작하지 않도록 Red 확인 후 구현을 맡긴다. 편집 범위를 나누고 다른 기능을 미리 시작하게 하지 않는다.
- “나중에 필요할 것”만을 이유로 프레임워크·공통 계층·자동화를 만들지 않는다. 실제 반복이나 현재 완료 조건에 근거한다.

## 한 단위 마무리

변경에 맞는 검증을 수행한다. 프로젝트 코드 변경은 `./gradlew.bat check`, 데이터만 변경하면 `verifySeeds`, 문서·스킬만 변경하면 링크·형식·작업 절차를 확인한다. macOS/Linux에서는 `./gradlew`를 사용한다. 테스트를 통과한 뒤에는 추가 변경이나 미해결 위험 없이 같은 검사를 반복하지 않는다.

변경 결과, Red에서 관찰한 실패 이유·명령, Green·리팩터링 후 검증 결과, 남은 제약을 [작업 기록](../../../docs/worklog.md)에 기록한다. TDD 적용 대상이 아닌 변경은 해당 이유와 실제 검증만 남긴다. 이슈/PR URL과 상태를 연결하고 구현·검증 완료와 머지·이슈 종료 완료를 구분한다. 성공·실패·미실행을 구분하며, 한 단위의 완료를 전체 단계 완료로 표시하지 않는다. 다음 단위가 의존하는 검증 실패는 먼저 해결하거나 미완료로 명시한다.

사용자가 전체 단계나 여러 결과를 요청했다면 **단위별 구현·검증을 순차 반복해 이미 요청한 범위를 끝까지 완료한다**. 작은 단위로 나눴다는 이유로 매번 승인을 받거나 첫 단위만 끝내고 중단하지 않는다. 한 단계씩 진행해 달라는 명시적 요청이 있으면 그 경계를 따른다. 실행에 필수인 정보가 없을 때만 필요한 질문을 하고 독립적인 준비는 계속한다.

최종 보고에는 이번 요청에서 완료한 단위, 실제 검증, 남은 작업을 간단히 구분한다. 커밋·푸시는 별도 사용자 지시와 범위에 따라 처리한다.
