**한국어 상품 검색 품질 실험실 — 기획 v0.2**

작성일: 2026-09-24. 현재 단계는 기획과 개발용 데이터 준비다. 검색 서비스 구현·실행·성능 측정은 아직 수행하지 않았다.

사용자가 확정한 목표는 **검색 엔지니어링·백엔드 포트폴리오**다. 의류 상의 도메인과 아래 기술 스택은 이를 위한 잠정 추천안이며, 사용자가 정한 기술 선호는 아직 없다. 주당 투자 시간도 미정이므로 날짜 대신 완료 조건으로 개발 단계를 관리한다.

프로젝트는 오타·별칭·속성이 섞인 상품 검색을 개선하고, 같은 조건에서 개선 전후를 재현하는 실험 도구다. 참고한 글의 질의 이해 → 검색 → 랭킹 → 로그 개선 구조를 작은 범위에 적용한다. [원문](https://leevigong.tistory.com/47)

**사용자 경험과 첫 범위**

대상 사용자는 상품명이나 표기를 정확히 기억하지 못하는 사람이다. 첫 상품 분야는 맨투맨·후드티·셔츠·니트·티셔츠로 제한한다. 사용자는 검색어를 입력하고 가격·색상·카테고리 필터로 결과를 좁힌다. 오타로 의심되면 원문 결과와 함께 다른 검색어를 제안받고, 선택했을 때만 다시 검색한다.

개발용 비교 화면에서는 같은 질의에 대한 기본 검색, 별칭 확장 검색, 랭킹 변경 결과를 나란히 보여준다. 오타 제안 후 결과는 별도 동작으로 표시한다. 입력 원문, 실제 실행 질의, 적용 규칙, 소요시간과 결과 ID를 확인할 수 있어야 한다.

| 우선순위 | 기능 | 완료 조건 |
|---|---|---|
| P0 | 상품 입력 검증·일괄 색인 | 잘못된 레코드를 식별하고 동일 ID를 중복 생성하지 않는다 |
| P0 | 기본 BM25 검색·필터 | 상품명·브랜드·카테고리·속성을 검색하고 필터 조건을 지킨다 |
| P0 | 별칭·정규화 | 검정/블랙, 흰색/화이트, 후디/후드티 사례를 처리한다 |
| P0 | 오타 후보 제안 | 자모·한영 입력 후보를 만들고 원문을 자동 대체하지 않는다 |
| P0 | 비교·평가 | 고정 질의와 기대 상품으로 방식별 결과를 저장한다 |
| P1 | 색인 교체·실패 복구 | 새 인덱스를 확인하고 전환하며 기존 인덱스로 복구할 수 있다 |
| P1 | 검색 이벤트 기록 | 검색·제안 선택·클릭을 요청 ID로 연결한다 |
| 후속 실험 | 자동완성·벡터 검색 | 먼저 확인한 실패 유형을 해결할 때 하나씩 추가한다 |

구매·결제·회원 기능, 판매량 기반 학습 랭킹, Kafka·CDC·Kubernetes는 현재 범위에서 제외한다. 로그가 쌓이기 전에는 클릭이나 매출 개선을 성과 지표로 삼지 않는다.

**기술 스택 추천안**

| 구성 | 잠정 선택 | 선택 목적 |
|---|---|---|
| API | Java + Spring Boot | 검색 요청, 검증, 오류 처리, 측정 코드를 한 애플리케이션에 둔다 |
| 검색 | Elasticsearch + Nori | 키워드 검색·분석기·필드별 가중치를 직접 제어한다 |
| 연결 | Elasticsearch 공식 Java API Client | 검색 DSL을 명시적으로 구성하고 관찰한다 |
| 실행 | Docker Compose | 검색 엔진과 애플리케이션의 실행 조건을 고정한다 |
| 화면 | 서버 제공 HTML + 소량의 JavaScript | 검색과 비교에 필요한 화면 두 개부터 구현한다 |
| 초기 원본·로그 | 버전 관리한 JSON + 로컬 JSONL | 작은 데이터로 시작하고 실행 결과를 파일로 비교한다 |

Spring Boot는 독립 실행과 상태 확인·메트릭 등 애플리케이션 운영 기능을 제공한다. Nori는 한국어 형태소 분석 플러그인이다. Elasticsearch는 공식 Java 클라이언트를 제공한다. [Spring Boot](https://docs.spring.io/spring-boot/index.html), [Nori](https://www.elastic.co/docs/reference/elasticsearch/plugins/analysis-nori), [Java 클라이언트](https://www.elastic.co/docs/reference/elasticsearch/clients/java)

특정 버전은 아직 고르지 않았다. 구현 시작 시 JDK·Spring Boot·클라이언트·Elasticsearch의 호환성을 확인하고 버전을 고정한다. 이미 익숙한 언어가 있으면 API 프레임워크를 바꾸어도 검색 설계와 평가 기준은 유지한다. 데이터 편집·다중 사용자가 필요해지는 단계에서 PostgreSQL 도입을 검토한다.

**검색 흐름과 비교 조건**

사용자 입력 → 입력 검증 → 정규화 → 원문 기반 후보 검색 → 정렬 → 결과와 교정 제안 반환.

원문 질의는 보존한다. 별칭 확장은 사전과 버전을 따로 관리하며 오타 제안으로 표시하지 않는다. 오타 후보 생성은 한영 키 변환과 자모 편집거리로 시작하고, 카탈로그 어휘와 후보 점수로 제안 여부를 결정한다. 정상 브랜드와 상품 코드의 정확한 일치를 우선 보호한다. 점수는 통계적으로 보정하기 전까지 정확한 확률로 표시하지 않는다.

| 비교 모드 | 설정 | 해석 |
|---|---|---|
| baseline | 동일 Nori 분석기·정규화, 동일 필터, 기본 BM25 | 모든 개선 비교의 기준 |
| query_v1 | baseline + 도메인 별칭 확장 | 질의 처리 효과 |
| ranking_v1 | query_v1 + 상품명·브랜드·속성 필드 가중치 | 랭킹 변경 효과 |
| suggestion_accepted | 제안 질의를 사용자가 선택한 뒤 위 모드로 검색 | 제안 선택을 가정한 결과이며 최초 검색 결과와 구별 |

처음에는 가중치를 고정해 비교하고 조정값을 기록한다. 분석기 자체를 바꾸는 실험은 별도 버전으로 분리한다. 임의 판매량이나 가짜 클릭 수를 랭킹의 실제 행동 근거로 사용하지 않는다.

API 초안은 GET /api/search와 POST /api/events 두 개다. 검색 요청에는 q, filters, mode, page, size를 두고, 응답에는 request_id, original_query, executed_query, suggestions, items, total, timing_ms, config_version, index_version을 둔다. 검색 모드와 디버그 정보는 비교 화면에서 사용한다. 후속 클릭 이벤트는 원래 검색 요청과 연결한다.

검색 엔진 오류는 결과 0건과 구분해 503 또는 504로 응답한다. 빈 질의·과도한 길이·잘못된 가격 범위를 검증하고 페이지 크기에 상한을 둔다.

**데이터와 기대 결과**

현재 준비된 파일은 아래와 같다.

- [가상 상품 50개](catalog-50.json): 5개 카테고리 각 10개. 상품 ID, SKU, 상품명, 브랜드, 색상, 소재, 핏, 안감, 소매, 사이즈, 가격, 활성 여부와 버전을 포함한다.
- [개발 시나리오 30개](search-scenarios-30.json): 정상·속성·필터·브랜드·코드 검색, 오타·한영 입력, 별칭, 정답 없는 검색과 적합 상품 ID를 포함한다.

상품과 가격은 이 기획을 위해 만든 가상 설정이다. 실제 상품이나 시장 데이터가 아니다. 비슷한 색상·핏·소재의 상품을 구별하는 파이프라인 검증에 사용한다. 규칙적으로 생성된 50개에서 얻은 수치를 실제 커머스 품질이나 대규모 성능으로 일반화하지 않는다.

30개 모두 개발용 시드다. 기대 결과는 명시한 속성 조건으로 지정한 초안이며 사람의 재검토를 거친다. 원본 스냅샷에만 유효하므로 데이터를 바꾸면 기대 결과도 다시 검토한다. 아직 검색을 실행한 결과나 품질 점수는 없다.

| 예시 | 기대 동작 |
|---|---|
| 블랙 반팔 티셔츠 | 블랙 긴팔 상품을 적합 결과로 세지 않는다 |
| 맨투먼 | 맨투맨을 제안하고, 선택 후 결과를 별도로 측정한다 |
| gnemxl | 후드티를 한영 입력 후보로 제안한다 |
| MONOLIT | 정상 영문 브랜드를 다른 한글 단어로 교정하지 않는다 |
| sw-001 | SKU의 대소문자를 정규화하되 오타로 표시하지 않는다 |
| 후드티 + 최대 1,000원 | 정답 0건. 가격 조건을 자동 완화하지 않는다 |

**평가 설계**

상품을 300~500개로 확장하고 질의를 총 100개 수준으로 늘리는 것이 다음 목표다. 예를 들어 개발용 60개와 최종 평가용 40개로 나눈다. 동일 의도의 원문·오타·별칭 변형은 intent_group 단위로 같은 집합에 둔다. 최종 평가셋은 튜닝 전에 동결하며, 가능하면 다른 사람이 작성한 질의와 관련성 판정을 포함한다. 혼자 판정한 경우 그 한계를 기록한다.

| 지표 | 분모·측정 조건 |
|---|---|
| Hit@5 | 정답이 있는 질의 중 상위 5개에 적합 상품이 하나 이상 있는 비율 |
| MRR@10 | 정답이 있는 질의별 첫 적합 상품 순위의 역수 평균. 10위 내 없으면 0 |
| 오타 제안 정확도 | 오타·한영 오류 질의 중 실제 제안을 낸 질의에서 1순위 제안이 정답인 비율 |
| 제안 커버리지 | 전체 오타·한영 오류 질의 중 제안을 낸 비율 |
| 정상 입력 오제안율 | 교정이 불필요한 정상 질의 중 잘못된 교정을 제안한 비율 |
| 정답 없음 처리 | 정답 없는 질의에서 무관 결과를 반환하거나 필터를 완화한 건수 |
| p95 응답시간 | 동일 기기·데이터 수·동시 요청 수·워밍업 조건에서 API 시간의 95백분위 |

제안 정확도는 제안이 0건이면 N/A로 표시한다. 커버리지와 함께 보아 아무것도 제안하지 않는 시스템을 우수하다고 평가하지 않는다. 30개 개발 시드에서는 오타·한영 오류 6개와 정상 입력 24개를 구분한다. 정답 없는 3개는 Hit@5·MRR 평균에서 제외하고 별도로 보고한다.

제안 후 검색 점수를 원문 검색 점수에 섞지 않는다. 제안 선택 후 실험은 잠재적 회복 효과이며 실제 이용자의 선택률을 증명하지 않는다. 넓은 탐색 질의의 순위 품질을 보려면 이후 0·1·2점 관련성 판정을 추가해 nDCG@10으로 평가한다. Elasticsearch의 평가 API는 질의와 문서별 판정값을 받아 MRR·DCG 등의 지표를 계산한다. [공식 평가 문서](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/search-rank-eval)

초기 성능 목표값은 기준 검색 측정 후 정한다. 완료 조건은 같은 조건에서 개선 여부를 보고하고, 정상 입력의 회귀·실패 사례·지연시간 비용을 함께 설명하는 것이다. 개선이 없으면 그 결과와 채택하지 않은 이유도 기록한다.

**색인 운영과 재현성**

상품 ID를 안정적인 문서 ID로 사용하고, 원본 JSON 스냅샷에서 새 인덱스를 만든다. 상품 수·ID·필수 필드와 대표 질의를 검증한 뒤 읽기 alias를 전환한다. 전환 전 실패 시 기존 인덱스를 유지하고, 전환 후 검증에 실패하면 기존 인덱스로 복구한다. Elasticsearch alias는 애플리케이션이 사용하는 인덱스를 바꾸는 데 사용할 수 있다. [공식 alias 문서](https://www.elastic.co/docs/manage-data/data-store/aliases)

Bulk 응답은 전체 HTTP 상태뿐 아니라 레코드별 오류를 확인한다. 실패 항목의 ID와 원인을 남기고 재시도해도 중복 문서가 생기지 않게 한다. 색인 생성 당시에는 고정 스냅샷을 사용하며 동시 변경분 동기화는 현재 범위에 넣지 않는다.

수정·삭제 반영은 다음 스냅샷 재색인으로 확인한다. 즉시 반영을 구현했다고 표현하지 않는다. 부하 시험은 품질 평가와 별개로 구성하고 데이터 수·동시성·측정 구간을 공개한다.

| M2 | 별칭·오타 후보·보호 규칙·검색 화면 | 사례별 적용 이유를 설명하고 원문/제안 검색을 구별한다 |
| M3 | 비교 실행·데이터 확대·최종 평가 분리 | 방식별 결과·지표와 대표 성공/실패 사례를 자동 저장한다 |
| M4 | 재색인 검증·복구·오류 처리·발표 자료 | 재실행·부분 실패·인덱스 전환 시연과 측정 조건을 문서화한다 |

첫 구현 작업은 M1이다. 세부 작업은 (1) 버전과 실행 명령 고정, (2) catalog-50.json 로더와 입력 검증, (3) Nori 분석 결과 확인 및 명시적 매핑, (4) 상품 ID 기반 일괄 색인, (5) 기본 검색·가격/색상/카테고리 필터 API, (6) 개발 시나리오 결과 저장 순서로 진행한다.

최종 포트폴리오에는 실행 가능한 코드, 검색 흐름 설명, 인덱스 설계 근거, 실험 비교표, 실패 사례, 재색인 복구 시연을 담는다. 기술 수보다 선택의 이유와 실제 검증 결과가 드러나도록 구성한다.
