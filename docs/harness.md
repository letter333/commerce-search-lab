# 개발·검색 평가 하네스

이 하네스는 작업 규칙, 개발 시드 검증, 검색 API 평가, 다음 작업 기록으로 구성한다. 하네스 준비가 M1 검색 서비스 구현 완료를 뜻하지 않는다.

## 시작하기

기본 개발 환경은 IntelliJ이며, IDE의 프로젝트·Gradle 실행에 JDK 21을 사용한다. 시스템 `JAVA_HOME` 설정을 IntelliJ 개발의 선행 조건으로 두지 않는다. Gradle은 저장소의 Wrapper를 사용한다. 최초 실행에는 배포본·Maven 의존성 다운로드가 필요하며 캐시가 준비된 환경에서는 `--offline`을 사용할 수 있다.

아래 명령을 터미널에서 직접 실행할 때는 해당 프로세스의 `JAVA_HOME`을 JDK 21로 지정하거나 PATH에서 JDK 21의 `java`를 찾을 수 있어야 한다.

```powershell
# 저장소 루트, Windows PowerShell
./gradlew.bat --version
./gradlew.bat verifySeeds
./gradlew.bat check
```

macOS/Linux에서는 같은 인수를 `./gradlew`에 전달한다. 실행 권한이 없으면 `sh ./gradlew check`로 실행한다. 현재 빌드에 기록된 버전은 Java 21, Spring Boot 4.1.1, Gradle 9.7.1이다. M1-01에서 ES·Nori 9.4.7과 Java Client·Rest5 9.4.5를 선정했다. 공식 근거와 인증/TLS·메모리·상태 판정은 [검색 엔진 실행 계약](search-engine-setup.md)을 따른다. 실제 엔진 기동은 M1-02, Client 의존성 적용·연결 검증은 M1-03에서 수행한다.

## 구성과 검증 수준

| 항목 | 역할 | 실행 또는 위치 |
|---|---|---|
| AI 작업 규칙 | 범위, 불변 조건, 검증·인계 기준 | `AGENTS.md` |
| 작업 기록 | 현재 상태, 완료 근거, 다음 작업 | `docs/worklog.md` |
| 시드 계약 | 개수, 유일 ID, 필수값, 기대 상품 연결·속성 일치, 교정 정책 | `verifySeeds` |
| 코드·평가 도구 테스트 | 앱 컨텍스트와 평가 계산·오류 처리의 회귀 검증 | `test` |
| 개발 완료 게이트 | `test`와 `verifySeeds` 모두 실행 | `check` |
| 실제 API 평가 | 시나리오별 응답과 모드별 품질 지표 저장 | `evaluateSearch` |

`verifySeeds`는 Elasticsearch와 Spring 컨텍스트 없이 실행한다. `test`에서는 seed 태그를 제외하므로 `check`에서 중복 실행하지 않는다. 기대 상품과 속성 조건의 기계적 일치 확인은 사람이 판정한 검색 관련성 검토를 대신하지 않는다.

평가 실행기는 테스트 소스와 클래스패스에서 실행하며 앱 JAR에 포함되지 않는다. 세부 요청·응답과 측정 규칙은 [평가 계약](evaluation-contract.md)을 따른다.

## 프로젝트 스킬

반복 작업에 필요한 절차는 저장소의 `.agents/skills/`에서 관리한다.

| 스킬 | 적용할 작업 |
|---|---|
| [commerce-search-small-steps](../.agents/skills/commerce-search-small-steps/SKILL.md) | 테스트를 먼저 작성하는 TDD, 검증 가능한 단위별 순차 완료, 불필요한 범위 확장 방지 |
| [commerce-search-git-delivery](../.agents/skills/commerce-search-git-delivery/SKILL.md) | 착수 전 이슈 등록, 작업별 이슈·PR 1대1 관리와 머지 후 종료, 커밋·푸시 전 범위·민감정보·검증·전송 대상 확인 |
| [commerce-search-evaluate](../.agents/skills/commerce-search-evaluate/SKILL.md) | 검색 평가 실행, 실패 보고서 해석, 재현 조건과 분모를 확인한 모드 비교 |
| [commerce-search-seeds](../.agents/skills/commerce-search-seeds/SKILL.md) | 상품·질의·기대값 수정, snapshot 버전 관리, 시드 계약 실패 진단 |

예: `$commerce-search-evaluate로 이 평가 결과를 검토해줘`, `$commerce-search-seeds로 후드티 상품 추가에 영향을 받는 시나리오를 확인해줘`.

개발 요청 예: `$commerce-search-small-steps로 M1을 테스트부터 작은 단위로 진행해줘`. Git 점검 요청 예: `$commerce-search-git-delivery로 커밋·푸시 전에 변경 사항을 점검해줘`.

작은 단위는 코드·테스트·문서가 함께 검증되는 결과를 기준으로 한다. 전체 단계가 요청되면 단위별로 순차 완료하며, 매번 재승인을 요구하지 않는다. Git 점검과 실제 커밋·푸시는 요청 범위를 구분하고 이미 받은 지시는 유지한다.

작업 커밋은 Conventional Commits의 `type(scope): 한국어 요약`과 후터 `Refs #실제이슈번호`를 사용한다. 한 PR 안에 검증 가능한 작은 커밋을 여러 개 쌓을 수 있으며, 이슈 종료 키워드는 PR 본문에만 둔다. 타입·scope·호환성 변경 표기와 이력 보존은 [Git 스킬의 커밋 규칙](../.agents/skills/commerce-search-git-delivery/SKILL.md#커밋-메시지와-단위)을 따른다.

실제 메시지와 본문 작성에는 [커밋·이슈·PR 템플릿](git-templates.md)을 사용한다. 이슈에는 착수 전 계획을, PR에는 실제 변경과 검증 결과를 기록한다.

관련 작업에는 자동 선택할 수 있게 두었다. 별도 도구 의존성이나 자동 실행 훅은 추가하지 않으며, 스킬은 기존 검증 코드와 문서를 참조한다. 저장소 스킬의 탐색 위치와 사용 방식은 [공식 스킬 안내](https://learn.chatgpt.com/docs/build-skills)를 따른다.

## 작업 루프

1. 작업에 필요한 기획 항목과 [작업 기록](worklog.md), 변경 중인 파일을 확인한다. 실제 착수 전 Git 전달 스킬로 해당 작업 ID의 이슈를 조회·등록하고 기존 PR을 확인한다. 스킬·지침·계획 작성만 요청받은 경우는 원격 작업을 실행하지 않는다.
2. 완료 기준이 명확한 동작 하나를 정하고 테스트부터 작성한다. 검색 변경은 실패 사례와 보호할 정상 사례를 함께 다룬다.
3. 새 테스트를 실행해 의도한 실패를 확인한 뒤 최소 구현으로 통과시킨다. 필요하면 통과 상태를 유지하며 리팩터링한다.
4. 데이터 계약이 바뀌면 시드와 검증 근거를 함께 검토한다. 코드 변경 단위가 끝나면 `check`를 실행한다.
5. 검색 API가 준비된 이후에는 동일 snapshot으로 평가한다. 개선 전·후 결과 폴더를 각각 보존한다.
6. 변경 내용, Red·Green의 명령과 실제 결과, 제약, 다음 작업을 `worklog.md`에 기록한다. 이슈/PR URL과 상태를 연결하고 구현·검증 완료와 머지·이슈 종료 완료를 구분한다. 문서 등 동작 변경이 없는 작업은 아래 적용 범위에 맞춰 확인한다.
7. 전달을 요청받으면 해당 이슈에 PR 하나만 생성하거나 기존 PR을 갱신한다. 이미 받은 권한 범위에서 진행하며, 실제 머지가 확인된 뒤 이슈 종료를 확인한다. PR이 머지 없이 닫힌 상태는 이슈 완료가 아니다.

## TDD 개발 기준

기능 추가·버그 수정·동작 변경의 기본 순서는 **테스트 작성 → 의도한 실패 확인(Red) → 최소 구현 → 통과 확인(Green) → 리팩터링**이다. 하나의 실패를 통과시킨 다음 다음 동작으로 넘어간다.

| 단계 | 실제로 확인할 것 |
|---|---|
| Red | 구현 전에 기대 동작을 검사하는 테스트를 작성·실행하고, 기능 부재나 잘못된 동작 때문에 실패했는지 확인한다. 버그는 수정 전 재현 테스트로 확인한다. |
| Green | 해당 실패를 통과시킬 최소 구현을 추가하고 동일 테스트가 실행되어 통과하는지 확인한다. |
| Refactor | 필요할 때만 중복·구조를 개선하고 영향받는 테스트로 통과 상태를 재확인한다. |
| 단위 완료 | 관련 회귀 테스트와 `check`를 통과하고 실제 Red·Green 결과 및 남은 제약을 기록한다. |

테스트는 입력과 관찰 가능한 결과·오류·경계 조건을 검증한다. 구현의 내부 구조나 mock 호출을 그대로 복제하지 않는다. 예를 들어 가격 상한 필터를 추가할 때는 상한과 같은 가격의 상품은 포함하고 이를 초과한 상품은 제외하는 테스트부터 작성한다. 의미 있는 검증 없이 커버리지 숫자를 채우지 않는다.

새 클래스·메서드가 없어 테스트가 실행되지 않으면 테스트를 먼저 작성한 뒤 필요한 최소 선언만 추가해 실행 가능한 실패로 만든다. JDK·의존성·Docker 접근 문제나 테스트 미발견은 원하는 동작의 실패 증거가 아니다. 실제 실행하지 못했으면 미실행으로 기록한다. 새 테스트가 처음부터 통과하면 기존 구현이 이미 요구를 충족하는지 확인하고 불필요한 코드를 추가하지 않는다. 일부러 잘못된 기대값을 넣어 실패를 만들지 않는다.

### 적용 범위

- **기능·버그·평가 도구 로직·데이터 검증 로직:** 위 TDD 순서를 적용한다. 기존 실패 테스트가 해당 요구를 정확히 재현하면 그것을 먼저 실행해 사용할 수 있다.
- **순수 리팩터링:** 동작을 유지하는 기존 테스트를 먼저 통과시키고, 검증이 부족하면 현재 동작을 보호할 테스트를 먼저 추가한다. 의도적인 실패를 만들 필요는 없다. 동작 변경은 별도 Red부터 다룬다.
- **실행 환경·인프라 설정:** 설정 전에 검증할 계약과 실행 가능한 상태 확인·통합 테스트를 준비하고 설정 후 실행한다. 엔진 연결 실패만으로 검색 로직의 Red를 확인했다고 주장하지 않는다.
- **문서·스킬·단순 시드 데이터 편집:** 문서·스킬은 형식·링크를 확인하고, 단순 시드 데이터 편집은 기존 `verifySeeds`로 검증한다. 형식적인 실패 테스트를 새로 만들지 않는다. 데이터 처리 동작도 바뀌면 그 로직에 TDD를 적용한다.

### 테스트 실행

개발 중에는 새 동작을 검증하는 클래스·메서드로 범위를 좁혀 피드백을 받고, 코드 변경 단위 완료 시 `check`로 확대한다. Windows 예시는 다음과 같다.

```powershell
# 기존 평가 테스트 예시. 새 동작 개발 시 먼저 작성한 테스트 클래스로 바꾼다.
./gradlew.bat test --tests 'org.letter33.commercesearchlab.evaluation.SearchEvaluatorTest'

# seed 태그 테스트는 별도 태스크로 실행한다.
./gradlew.bat verifySeeds

# 코드 변경 단위의 완료 게이트
./gradlew.bat check
```

일반 `test`는 seed 태그를 제외한다. 잘못된 태스크를 실행해 테스트가 선택되지 않은 상태를 통과로 취급하지 않는다. 실행된 테스트 수와 결과를 확인한다. macOS/Linux에서는 `./gradlew`를 사용한다.

과거의 테스트 통과 기록만으로 테스트를 먼저 작성했다고 소급해서 주장하지 않는다. Red 단계의 실패는 개발 증거이며, 일반 커밋·푸시 대상은 Green과 필수 검증을 마친 변경이다.

작은 문서 수정까지 별도 계획서를 만들 필요는 없다. 설계 선택이 남는 작업은 아래 양식을 작업 기록에 사용한다.

```markdown
### 작업 ID · 제목
- 목적 / 관련 기획:
- 이슈 URL / 작업 브랜치 / PR URL / 대상 브랜치:
- 구현·검증 상태 / PR 머지 상태·SHA / 이슈 종료 상태:
- 완료 기준:
- 먼저 작성한 테스트 / 기대한 실패:
- Red 명령 / 실제 실패 이유:
- 변경 사항 / 선택 근거:
- Green·리팩터링·최종 검증 명령 / 실제 결과 / 산출물:
- TDD 적용 대상이 아닌 경우 이유 / 대신 수행한 검증:
- 남은 제약:
- 다음 작업:
```

## 단계별 통과 기준

| 단계 | 통과에 필요한 증거 |

| H0 · 하네스 | 시드 계약 통과, 평가 계산·실패 처리 테스트 통과, 실행 계약·작업 기록 준비 |
| M0 · 개발 시드 | 50개·30개 연결과 속성 일치 확인 + 사람의 관련성 판정 검토 기록 |

| M2 · 질의 개선 | 별칭과 오타 제안 분리, 정상 브랜드/SKU 보호, 원문·제안 선택 화면, 모드별 성공·실패 사례 |
| M3 · 비교 평가 | 300~500개 상품·약 100개 질의, intent_group 단위 분할, 최종셋 동결, 모드별 비교 및 지연 비용 |
| M4 · 운영·발표 | Bulk 부분 실패·재시도, 새 인덱스 검증·alias 전환·복구 시연, 503/504·입력 오류 처리, 재현 문서 |

지금은 품질 임계값을 임의로 정하지 않는다. 첫 실제 baseline 이후 비교 기준을 정한다. HTTP·응답 계약 오류로 평가가 불완전한 실행은 품질 개선의 근거로 채택하지 않는다.

## 산출물과 증거

- 테스트: `build/reports/tests/test/index.html`, `build/reports/tests/verifySeeds/index.html`.
- 검색 평가: 기본 `build/evaluations/<실행 시각>/`의 `manifest.json`, `runs.jsonl`, `summary.json`.
- `build/`는 임시 산출물이며 Git에서 제외된다. 발표에 사용할 실제 실행은 별도 결과 폴더에 세 파일을 함께 보존하고 출처·실행 명령·한계를 문서화한다.
- `clean`은 `build/`를 삭제한다. 보존할 평가 결과는 `clean` 전에 다른 위치로 복사한다.

AI 작업 지침은 루트 `AGENTS.md`에 짧게 두고 필요한 문서를 연결한다. 위치·적용 방식은 [공식 AGENTS.md 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md)를 참고했다.
