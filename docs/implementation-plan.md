# 구현 실행 계획 v1

작성일: 2026-09-24. 갱신일: 2026-09-25. 상태: **M1-02 ES/Nori 기동·재기동 검증 완료, 다음은 M1-03 공식 Client 연결**. 전달·머지 상태는 작업 기록을 따른다.

이 문서는 [제품 기획](search-project-plan.md)을 실제로 실행할 작은 작업으로 나눈다. 현재 상태와 실제 실행 결과는 [작업 기록](worklog.md), 개발 절차는 [하네스](harness.md), 검색·평가 인터페이스는 [평가 계약](evaluation-contract.md)을 기준으로 한다. 아래 테스트·파일·명령 중 아직 없는 것은 구현 예정이며, 테스트 성공이나 검색 품질을 미리 뜻하지 않는다.

## 1. 출발점과 계획 범위

| 구분 | 현재 확인한 상태 | 계획에서의 처리 |
|---|---|---|
| 실행 골격 | Java 21, Spring Boot 4.1.1, Gradle Wrapper 9.7.1 | 기존 버전 유지. ES·Nori·공식 Java Client만 호환성을 확인해 고정 |
| 제품 코드 | 앱 진입점과 기본 설정 | 카탈로그 로더부터 새로 구현 |
| H0 하네스 | `verifySeeds`, `check`, `evaluateSearch`와 테스트 존재 | 재사용. 평가 실행기를 새로 만들지 않음 |
| 과거 검증 | 작업 기록에 118개 테스트 통과 기록 | 이번 계획 작성에서 재실행한 결과와 구별 |
| 개발 데이터 | 상품 50개, 질의 30개 | 초기 기능 검증용. 사람의 관련성 검토는 별도 필요 |
| 실제 검색 | API·색인·실측 품질 없음 | M1에서 최초 실행 증거 확보 |
| 화면·이벤트·색인 교체 | 미구현 | 필요한 시점에 작은 단위로 추가 |

완성할 결과는 **같은 조건에서 baseline → query_v1 → ranking_v1을 비교하고, 원문 검색·명시적인 제안 선택·실패·색인 복구를 재현하는 검색 포트폴리오**다. 결제·회원·Kafka·CDC·Kubernetes·벡터 검색·별도 프런트엔드 프레임워크는 이번 계획에 포함하지 않는다. 자동완성과 nDCG는 실제 실패 분석이나 등급 판정 데이터가 생긴 뒤 별도 계획으로 다룬다.

주당 투자 시간이 정해지지 않았으므로 날짜나 확정 소요일 대신 선행 조건과 완료 증거로 진행한다. M1 이후 세부 구현은 실제 토큰과 실패 사례를 근거로 조정하되, 평가 분모나 보호 규칙을 통과를 위해 약화하지 않는다.

### H0-01 · 기존 개발·평가 기반의 최초 Git 전달

- **선행:** 로컬에서 작성·검증한 H0 하네스와 구현 준비 문서. **결과:** 검증 가능한 초기 기준선을 작업 이슈 하나와 PR 하나로 전달한다.
- **범위/검증:** 기존 Java/Gradle 골격·개발 시드·평가 도구·계약·계획·스킬·템플릿을 검토하고, 실제 테스트 결과·문서 링크·민감정보 제외·index 일치·Wrapper 실행 모드를 확인한다. 새 M1 구현이나 과거 Red 기록의 소급 작성은 포함하지 않는다.
- **전달 상태:** 실제 이슈/PR과 커밋·푸시·머지 상태는 [작업 기록](worklog.md)에 남긴다. 아래 101개 후속 구현 작업의 수와 ID는 유지한다.

## 2. 작업 단위 운영

한 작업 ID는 관찰 가능한 결과 하나와 이를 검증하는 코드·테스트·문서를 포함한다. 여러 테스트 사례가 있으면 **각 사례별 Red → Green을 순서대로** 진행한다. 한 ID 안에서도 서로 독립적인 기능이 발견되면 `M1-06a`, `M1-06b`처럼 나누고 선행 관계를 갱신한다. 단위를 작게 나눈 것이 매번 사용자 승인을 받는다는 뜻은 아니다.

실제 착수 전 [Git 전달 스킬](../.agents/skills/commerce-search-git-delivery/SKILL.md)로 최종 작업 ID의 이슈를 등록하거나 재사용한다. **작업 ID 하나·이슈 하나·PR 최대 하나**로 관리하고 후속 커밋은 같은 PR에 반영한다. 실제 PR 머지 후 이슈 종료를 확인하며, 구현·검증 상태와 머지·종료 상태는 따로 기록한다. 스킬·지침·계획 작성만 요청받은 경우에는 그 문서 작업을 수행하며 실제 이슈/PR을 생성하지 않는다.

새 테스트가 처음부터 통과하면 기존 구현이 요구를 충족하는지 확인해 재사용한다. 인위적으로 실패시키지 않는다. 순수 리팩터링은 기존 동작 테스트의 통과를 먼저 확인하고 부족한 보호 테스트를 보강한다.

1. 작업 기록·현재 변경·선행 작업의 증거를 확인하고, 실제 착수라면 해당 작업 이슈와 기존 PR을 확인한다.
2. 이번 결과, 먼저 작성할 테스트, 기대하는 실패 이유를 짧게 알린다.
3. 동작 테스트를 작성하고 실행해 실제 실패를 확인한다. 컴파일·JDK·Docker 오류는 동작의 Red가 아니다.
4. 해당 테스트를 통과시키는 최소 구현 후 필요할 때만 리팩터링한다.
5. 작업에 필요한 검증과 `check`를 실행하고 실제 결과를 기록한다.
6. 현재 ID를 완료한 뒤 다음 ID를 활성화한다. 요청받은 범위 안에서 계속 진행한다.

문서·환경·데이터 작업에는 형식적인 실패 테스트를 만들지 않는다. 환경은 먼저 점검 계약을 준비한 뒤 실제 기동으로 확인한다. 데이터 검증 로직을 변경하면 그 로직은 TDD 대상이다. 구현 중 관련성 검토가 필요하면 검토 자료를 준비하고 독립적인 환경·기능 작업은 계속할 수 있다.

**모든 작업의 민감정보 기준:** 실제 환경변수 파일·자격증명·개인키·민감한 원문 로그는 Git에 포함하지 않는다. 비밀값은 실행 환경에서 주입하고, 공유 설정은 환경변수 참조, 루트 `.env.example`은 빈 값/placeholder만 사용한다. 새 로컬 파일은 `git check-ignore`로 제외 여부를 확인한다. 커밋 전 변경·staged 내용과 푸시 전 전송 이력을 값 노출 없이 검토한다. `.gitignore`만으로 이미 추적된 파일이나 이력이 정리되지는 않는다. 상세 기준은 [작업 지침](../AGENTS.md#민감정보와-git)을 따른다.

### 공통 완료 증거

| 작업 종류 | 단위 완료에 필요한 증거 |
|---|---|
| 코드·평가 동작 변경 | 목표 테스트의 실제 Red·Green 또는 기존 충족 근거, 관련 회귀, `./gradlew.bat check` |
| 순수 리팩터링·환경용 Gradle 설정 | 기존 동작/실행 계약 확인, 변경 후 관련 검증과 `./gradlew.bat check` |
| ES 검색·매핑·색인 | 위 검증 + 고정 버전 실제 엔진의 통합 테스트. mock만으로 완료하지 않음 |
| 데이터만 변경 | `./gradlew.bat verifySeeds`, snapshot/version, 변경 이유와 관련성 검토 기록 |
| 화면 | 해당 API 테스트 + 브라우저에서 입력·선택·오류·상태 전환 확인 |
| 문서·계획 | 경로·링크·명령·선행 조건 일관성 확인 |
| 실제 평가 | 종료 상태, `manifest.json`·`runs.jsonl`·`summary.json`, 유효성·분모·버전 확인 |

작업 기록에는 ID, 이슈/PR URL과 브랜치·머지/종료 상태, 목적, Red 명령/실패 이유, 변경/근거, Green/최종 검증, 산출물, 제약, 다음 ID를 남긴다. `완료 / 진행 중 / 대기 / 환경으로 미실행`을 구분한다. 계획 문서의 체크 여부만으로 완료를 선언하지 않는다.

### 테스트 구분과 실행

| 표기 | 의미 | 실행 방식 |
|---|---|---|
| D | 문서·설계 검토 | 링크·결정 근거·계약 사례 확인 |
| E | 실행 환경 점검 | 버전, Compose 구성, 엔진 상태, Nori 설치 확인 |
| U | 순수 동작 테스트 | 기존 `test --tests '전체.클래스명'` |
| W | HTTP 경계 테스트 | 기존 `test`에서 요청·상태 코드·JSON 검증 |
| I | 실제 Elasticsearch 통합 | M1-03에서 추가할 `integrationTest` |
| S | 시드 계약 검사 | 기존 `verifySeeds` |
| B | 브라우저 동작 확인 | 재현 입력·예상 화면·관찰 결과 기록 |
| Q | 실제 API 평가 | 기존 `evaluateSearch` |

`integrationTest`는 **현재 없는 예정 태스크**다. M1-03에서 클라이언트 연결 테스트를 준비할 때 기존 Gradle에 최소 태스크/태그 분리를 먼저 추가하고 `src/test`의 ES 태그 테스트를 실행한다. M1-04에서 테스트 인덱스 격리를 준비한다. 기존 `check`는 외부 서비스 없이 실행 가능한 상태를 유지하되, ES 변경의 완료에는 별도로 I 통과가 필요하다. 엔진이 없으면 I를 성공으로 건너뛰지 않고 미실행 또는 실패로 기록한다. `evaluateSearch`도 `check`에 연결하지 않는다.

현재 사용할 수 있는 명령:

```powershell
./gradlew.bat --version
./gradlew.bat verifySeeds
./gradlew.bat test --tests 'org.letter33.commercesearchlab.evaluation.SearchEvaluatorTest'
./gradlew.bat check
./gradlew.bat evaluateSearch --args="--help"
```

API와 엔진 구현 후 사용할 명령:

```powershell
# M1-03 구현 후에만 존재하는 예정 태스크
./gradlew.bat integrationTest

# 서버는 별도 실행. 결과 폴더는 매번 새 이름 사용
./gradlew.bat evaluateSearch --args="--base-url http://localhost:8080 --modes baseline --output build/evaluations/m1-baseline-01"

# M2에서 세 모드와 제안 기능이 구현된 뒤 실행
./gradlew.bat evaluateSearch --args="--base-url http://localhost:8080 --modes baseline,query_v1,ranking_v1 --accept-suggestions --output build/evaluations/m2-comparison-01"
```

## 3. 단계와 선행 관계

| 단계 | 작업 수 | 사용자가 확인할 결과 | 다음 단계로 넘어갈 기준 |
|---|---|---|---|
| M0 후속 | 2 | 개발 기대값 검토 근거 | 자동 검사와 사람의 판정 기록을 구분 |
| M1 | 36 | 50개를 적재하고 baseline·필터 API 실행 | 환경 고정, 실토큰·매핑, 재실행, 오류 처리, 실제 평가 세 파일 |
| M2 | 20 | 별칭·오타 제안·고정 가중치와 화면 | 정상 입력 보호, 원문/제안 분리, 세 모드 비교 가능 |
| M3 | 23 | 확대 데이터에서 동결된 조건으로 비교 | 상품 300개 이상, 약 100개 질의, 의도 그룹 분리, final 동결과 실제 결과 |
| M4 | 20 | 색인 복구·이벤트 연결·재현 시연 | 부분 실패 재시도, 교체/복구, 측정 조건, 따라 할 수 있는 문서 |

총 **101개 작업**이다. 작업 수는 일정 추정치가 아니라 검증과 인계의 경계다. 더 나눌 필요가 있으면 기존 ID를 보존하며 하위 ID를 추가한다.

기본 순서는 `M1 → M2 → M3 → M4`다. M0의 사람 검토는 M1의 환경 준비와 병행할 수 있다. M1의 오류 응답·Bulk 항목 실패 확인은 평가 신뢰성에 필수이므로 M4로 미루지 않는다. `ranking_v1`은 M2에서 구현하고 M3에서 개발셋을 기준으로 평가·조정한다. M4는 M1의 안전한 최초 alias 연결을 확장해 기존 인덱스 교체와 복구를 구현한다.

### M0 후속 — 개발 기대값의 근거

#### M0-01 · 사람이 검토할 관련성 목록 준비

- **선행:** 현재 50개·30개 파일. **결과:** 질의별 의도, 적합/부적합 ID, 경계 사례와 판정 근거를 한곳에서 확인한다.
- **검증(D/S):** Q012의 반팔/긴팔 구분, Q011의 울 혼방 포함, Q025의 도메인 한정 별칭, Q028~Q030의 정답 없음이 원본과 일치한다.
- **범위/완료:** 검토 자료만 준비한다. AI의 속성 일치 검사를 사람의 판정으로 표시하지 않는다.

#### M0-02 · 사람의 검토 결과 기록

- **선행:** M0-01 및 실제 검토자 피드백. **결과:** 검토자·일자·검토 범위·이견·수정 이유가 남는다.
- **검증(D/S):** 변경된 기대 ID가 카탈로그와 맞고 snapshot/version 정책을 지킨다. 데이터 수정 시 seeds 스킬과 `verifySeeds`를 사용한다.
- **범위/완료:** 피드백 전에는 대기 상태다. 검토 전 실제 검색을 돌릴 수는 있지만 결과를 미검토 개발 초안 진단으로만 표시한다.

## 4. M1 — 기본 검색을 실제로 실행하기

### 실행 환경

#### M1-01 · 버전 조합과 실행 계약 확정

- **세부 실행 순서:** [M1-01 세부계획](m1-01-plan.md). 한 이슈 안에서 기반 확인부터 버전 선정·실행 계약·검증 설계·전달까지 순서대로 진행한다.
- **작성 결과:** [실행 계약](search-engine-setup.md), [이슈 #3](https://github.com/letter333/commerce-search-lab/issues/3). ES·Nori 9.4.7 + Java Client·Rest5 9.4.5를 선정했다. 문서상 선정과 실제 실행 검증을 구분한다.
- **선행:** 없음. **결과:** 기존 Java/Boot/Gradle과 함께 사용할 ES·Nori·공식 Java Client의 고정 조합을 문서화한다.
- **먼저 확인(E/D):** 설치 JDK·Wrapper·Docker/Compose 가용성, 공식 호환 문서, 클라이언트 전송/JSON 의존성 충돌 여부를 점검한다. 최신이라는 이유로 버전을 고르지 않는다.
- **범위/완료:** 버전표·공식 근거 링크·로컬 접속/포트/메모리 요구·상태 확인 기준을 남긴다. 실제 의존성 연결은 M1-03에서 확인하며, 문서 조사만으로 호환 검증 완료라 하지 않는다.

#### M1-02 · Nori 포함 검색 엔진 기동

- **실행 결과:** [로컬 실행 안내](local-elasticsearch.md), [이슈 #5](https://github.com/letter333/commerce-search-lab/issues/5). ES/Nori 9.4.7·TLS/인증·green·재기동 보존 확인. Windows 보완과 호스트 제약은 작업 기록에 남겼다.
- **선행:** M1-01. **결과:** 고정한 ES 버전과 같은 버전의 Nori가 설치된 엔진을 Compose로 실행한다.
- **먼저 확인(E):** 구성 검증 → 엔진 응답 → 버전 → 플러그인 목록 순서의 점검을 준비한다. 단일 노드의 replica/health 기준을 명시한다.
- **범위/완료:** Dockerfile·Compose·환경 예시와 시작/중지 명령. `latest` 사용 없이 재기동 가능하며, 로컬용 포트·인증 설정의 범위가 문서와 일치한다. 실제 `.env`는 제외하고 루트 `.env.example`에는 빈 값/placeholder만 둔다. Compose에 비밀값을 직접 쓰지 않으며 `git check-ignore`로 실제 설정의 제외 여부를 확인한다.

#### M1-03 · 공식 Java Client 연결

- **선행:** M1-02. **결과:** 앱 설정으로 접속한 클라이언트가 실제 엔진 버전을 읽는다.

- **범위/완료:** 필요한 클라이언트 의존성·설정·자원 종료. 실제 선택 버전의 직렬화/전송 경로가 실행되고 엔진 없이 기존 `check`가 통과한다. 테스트 실행 수가 0개이거나 엔진이 없을 때 통합 검증을 성공으로 처리하지 않는다.

#### M1-04 · 실제 엔진 테스트의 인덱스 격리

- **선행:** M1-03. **결과:** 실제 엔진 테스트가 서로와 개발용 인덱스에 영향을 주지 않는다.

- **범위/완료:** 로더 입력 계약과 오류 목록. 하나라도 잘못된 스냅샷은 색인 작업에 넘기지 않는다.

- **범위/완료:** 스냅샷 전체의 유일성 검증. 마지막 레코드로 조용히 덮어쓰지 않는다.

#### M1-08 · 입력 버전과 해시 연결

- **선행:** M1-07. **결과:** 로딩한 원본 바이트의 SHA-256·dataset_id·schema_version을 색인 입력과 함께 유지한다.

- **범위/완료:** 한 번 읽은 고정 스냅샷을 후속 색인에 전달한다. 파일명만으로 데이터 버전을 대신하지 않는다.

- **범위/완료:** 모든 조건이 total과 items에 함께 적용된다. 모드가 추가돼도 재사용할 회귀 테스트를 남긴다.

#### M1-23 · 페이지와 순위 재현

- **선행:** M1-22. **결과:** page=1부터 시작하고 size에 맞춰 안정적인 순위와 정확한 total을 반환한다.
- **먼저 작성(I):** 동일 점수 상품의 고정 ID 보조 정렬, 연속 페이지 중복 없음, 마지막/범위 밖 페이지, total은 페이지 크기와 별개.
- **범위/완료:** `_score` 뒤 안정 ID 정렬, 정확 total 조회, 허용 최대 결과 범위. deep pagination 지원을 새로 확장하지 않는다.

### HTTP API와 실제 baseline

#### M1-24 · 검색 HTTP 성공 계약

- **선행:** M1-23. **결과:** `GET /api/search`가 기존 평가 실행기가 읽을 수 있는 200 JSON을 반환한다.
- **먼저 작성(W):** UTF-8 `q`, 평탄한 필터, mode/page/size 바인딩과 필수 응답 필드 타입, 정상 0건의 `items: []`, `suggestions: []`.
- **범위/완료:** DTO·컨트롤러·서비스 연결과 실제 request_id/시간/config/index 출처를 함께 구현한다. 임시 버전 문자열로 성공 계약을 채우지 않는다. 미지정 기본값과 상품 응답 필드를 계약에 적고 기존 실행기와 맞춘다.

#### M1-25 · 검색어 입력 오류

- **선행:** M1-24. **결과:** 누락·빈 문자열·공백뿐인 입력·길이 제한 초과를 일관된 4xx로 반환한다.
- **먼저 작성(W):** 한계 길이의 양쪽 경계와 원문 보존. 검증 실패 요청이 검색을 실행하지 않는지 확인한다.
- **범위/완료:** 길이 기준의 문자 계산 방식, 오류 코드·필드·설명·request_id를 계약화한다. 실제 제한값은 이 단위에서 이유와 함께 고정한다.

#### M1-26 · 필터 입력 오류

- **선행:** M1-25. **결과:** 음수/비정수/overflow 가격, 역전된 가격 범위, 빈 필터를 명확한 4xx로 처리한다.
- **먼저 작성(W):** `price_min > price_max`, 잘못된 숫자, 지원하지 않는 필터 파라미터의 합의된 거절 동작. 정상 미보유 값은 여전히 200/0건이다.
- **범위/완료:** 값/타입 오류와 검색 결과 없음을 구분한다. 입력을 임의로 보정하지 않는다.

#### M1-27 · 모드·페이지 입력 오류

- **선행:** M1-25. **결과:** 미구현/알 수 없는 mode, page<1, size 상한 초과, 허용 범위 밖 offset을 거절한다.
- **먼저 작성(W):** M1에서 `query_v1`/`ranking_v1` 요청을 baseline으로 조용히 바꾸지 않음, 경계·overflow 사례.
- **범위/완료:** 기본값과 제한을 문서화한다. M2에서 구현한 모드만 차례로 허용한다.

#### M1-28 · 응답 출처와 시간의 경계 검증

- **선행:** M1-24, M1-11. **결과:** 0건과 반복 요청에서도 실제 실행과 보고한 출처가 일치한다.
- **먼저 작성(W/I):** 결과가 없어도 실제 인덱스 버전 확인, 요청별 식별자, 공백 원문 유지, 음수 시간 방지, 설정과 생성 기록 대조.
- **범위/완료:** M1-24 구현을 보호하는 경계 테스트와 필요한 수정. 요청에서 실제 대상 인덱스를 한 번 확정하고 조회와 버전 표시에 같은 대상을 사용한다. 이미 통과하면 근거를 기록하고 불필요한 코드를 추가하지 않는다. ES 처리 시간·서버 시간·평가기의 HTTP 시간을 구분한다.

#### M1-29 · 검색 엔진 장애 응답

- **선행:** M1-28. **결과:** 연결 실패·엔진 사용 불가를 503으로 반환한다.
- **먼저 작성(W/I):** 통신 오류와 정상 0건을 구분하고 장애 시 성공 JSON/빈 결과로 감싸지 않음을 확인한다.
- **범위/완료:** 일관된 오류 응답과 제한된 진단 로그. 엔진 내부의 민감한 접속 정보를 응답에 포함하지 않는다.

#### M1-30 · 시간 초과·불완전 검색 응답

- **선행:** M1-29. **결과:** 요청/엔진 시간 초과는 504, 그 밖의 shard 실패 등 불완전 결과는 명시적인 실패로 반환한다.
- **먼저 작성(W/I):** 클라이언트 timeout, ES `timed_out`, 일부 shard 실패를 구분한다. 부분 결과를 정상 품질 평가에 전달하지 않는다.
- **범위/완료:** 제한 시간과 상태 코드 매핑. 결정적인 오류 fixture를 우선 사용하고 실제 엔진의 정상 경로도 확인한다.

#### M1-31a · 로컬 앱 실행 절차 연결

- **선행:** M1-01~M1-30의 모든 작업. **결과:** 문서의 순서대로 엔진 기동 → 적재/검증 → 로컬 앱 실행 → 검색이 된다.
- **먼저 확인(E/I):** 새 이름의 인덱스와 환경 예시로 시작해 HTTP 대표 질의까지 실행한다. 컨테이너 내부 ES 주소와 호스트 주소를 구분한다.
- **범위/완료:** 로컬 `bootRun` 실행 경로를 문서화한다. 기존 볼륨/인덱스를 삭제해야만 재현되는 절차를 기본으로 삼지 않는다.

#### M1-31b · 앱 포함 Compose 실행

- **선행:** M1-31a. **결과:** 패키징한 앱과 ES를 Compose 환경에서 함께 실행한다.
- **먼저 확인(E/I):** 앱 이미지 빌드, 환경 설정 전달, 컨테이너 간 ES 주소, 호스트의 검색 API 호출과 대표 응답.
- **범위/완료:** 앱 Dockerfile과 Compose 연결, 실행/중지 절차. 앱 기동이 검증 없이 alias를 교체하거나 자동 재색인하지 않는다.

#### M1-32 · 최초 실제 baseline 평가

- **선행:** M1-31b. **결과:** 실제 API에 개발 질의 30개를 실행하고 평가 세 파일을 얻는다.
- **먼저 확인(Q/S):** evaluate 스킬로 입력 해시·설정·인덱스·실패를 확인한다. 현재 원문 Hit/MRR 대상 27개, 오류 질의 6개, 정상 24개, 정답 없음 3개를 구분한다.
- **범위/완료:** `valid: true`는 실행 계약 충족이고 높은 품질을 뜻하지 않는다. 오류가 있으면 해당 원인을 먼저 해결한다. M0-02 미완료 시 미검토 기대값에 대한 진단임을 명시한다.

#### M1-33 · baseline 실패 목록과 비교 기준

- **선행:** M1-32. **결과:** 어떤 입력이 왜 실패했는지와 M2에서 확인할 개선 가설을 정리한다.
- **검증(D/Q):** 토큰·반환 ID·필터·설정 근거로 실패를 분류하고 원문/제안 점수를 섞지 않는다. 제안 0건의 정확도는 N/A다.
- **범위/완료:** 대표 성공/실패, 정상 입력 회귀 확인 항목, 같은 조건의 시간 비교 방법을 기록한다. 세 원본 산출물은 `clean` 전에 별도 결과 경로에 함께 보존한다.

**M1 완료 게이트:** `check` + 실제 I + 실행 문서 + 유효한 실제 baseline 기록. 관련성 검토 미완료는 별도 제약으로 남긴다. 품질 개선이나 성능 목표 달성을 미리 주장하지 않는다.

## 5. M2 — 질의 개선과 검색·비교 화면

### 별칭과 실행 이유

#### M2-01 · 세 모드의 차이와 제안 정책 고정

- **선행:** M1-33. **결과:** 세 모드 사이에서 무엇이 바뀌는지와 실행 질의 표현을 명확히 한다.
- **검증(D):** baseline은 기본 질의, query_v1은 별칭 확장 추가, ranking_v1은 그 위에 필드 가중치만 변경한다. 분석기·정규화·필터·동점 정렬·제안 정책은 동일하다.
- **범위/완료:** 별칭 규칙 ID와 실행 표현의 예시, 원문 보존, 디버그 응답의 선택 필드를 계약에 적는다. 오타+별칭 혼합 입력은 기존 `suggest_only` 보호를 완화하지 말고 별도 후속 계약으로 남긴다.

#### M2-02 · 버전 있는 별칭 사전 로드

- **선행:** M2-01. **결과:** 검정/블랙, 흰색/화이트, 후디/후드티, 도메인 한정 스웨터/니트 규칙을 읽는다.
- **먼저 작성(U):** 정상 사전, 빈 규칙, 중복/상충 규칙, 지원하지 않는 버전 거절. 한 번의 비재귀 확장으로 순환 적용을 피한다.
- **범위/완료:** 명시적 사전 파일과 도메인 근거. 시나리오의 정답 ID나 기대 제안을 제품 코드에서 읽지 않는다.

#### M2-03 · 토큰 경계의 별칭 확장

- **선행:** M2-02, M1-16. **결과:** 검색어 토큰에 해당하는 별칭만 원어와 대안의 관계로 확장한다.
- **먼저 작성(U):** `검정 후디`에 두 규칙 적용, 부분 문자열 오치환 방지, 중복 확장 제거, 원문/정상 브랜드·SKU 보존.
- **범위/완료:** 실행용 질의 계획과 적용 규칙 ID. `suggestions`에는 별칭을 넣지 않으며 단순 문자열 치환이 검색 의도를 바꾸지 않는지 검증한다.

#### M2-04 · query_v1 실제 검색

- **선행:** M2-03, M1-27. **결과:** 같은 인덱스에서 query_v1만 별칭 확장 검색을 수행한다.
- **먼저 작성(I/W):** 통제 fixture에서 별칭 검색의 후보 회복, baseline 동작 유지, 가격·색상·카테고리의 교집합 유지, 오타 원문 자동 대체 없음.
- **범위/완료:** 새 mode 허용과 config_version. 실제 DSL의 의미와 `executed_query`/규칙 표시가 일치한다. 별칭 처리에 분석기 재색인을 섞지 않는다.

### 오타 후보와 정상 입력 보호

#### M2-05 · 카탈로그 후보 어휘 만들기

- **선행:** M1-08, M2-01. **결과:** 현재 카탈로그의 상품·카테고리·브랜드 어휘로 후보 사전을 구성한다.
- **먼저 작성(U):** 중복 어휘 제거, 빈 값 제외, snapshot 변경 시 어휘/버전 변경. 정답 시나리오 파일 없이도 생성돼야 한다.
- **범위/완료:** 후보/보호 어휘와 출처 해시를 snapshot별로 연결한다. 검색한 인덱스와 다른 snapshot의 어휘를 사용하지 않는다. 최종 질의/판정 데이터에서 어휘를 추출하지 않는다.

#### M2-06 · 보호 어휘 우선 판정

- **선행:** M2-05, M2-02. **결과:** 정상 브랜드·SKU·정상 어휘·등록 별칭을 교정할 필요가 없는 입력으로 구분한다.
- **먼저 작성(U):** `MONOLIT`, `SW-001`, `sw-001`, `라온웨어`, `후디`에 오타 제안 없음. 브랜드가 포함된 복합 입력에서도 보호 부분을 변경하지 않는다.
- **범위/완료:** 후보 변환 전에 보호 판정한다. 정상 입력을 전부 영문 키보드 오류로 처리하지 않는다.

#### M2-07 · 한영 키 입력 후보

- **선행:** M2-06. **결과:** 잘못된 키보드 언어로 입력한 문자열에서 한글 후보를 만든다.
- **먼저 작성(U):** `gnemxl → 후드티`, `aosxnaos → 맨투맨`, 변환할 수 없는 입력·숫자·혼합 입력 경계. 보호 어휘 우선 규칙 회귀.
- **범위/완료:** 필요한 두벌식 키 매핑과 조합만 구현한다. 후보 생성은 검색 실행과 분리하고 변환했다는 이유만으로 제안하지 않는다.

#### M2-08 · 자모 분해와 편집거리

- **선행:** M2-06. **결과:** 한글 단어의 자모 수준 차이를 일관되게 계산한다.
- **먼저 작성(U):** 동일 단어 거리 0, 삽입/삭제/치환, 받침 차이, 영문/숫자/빈 입력 처리. 구체적인 거리 정의를 먼저 고정한다.
- **범위/완료:** 순수 계산 함수. 상품별 정답이나 검색 횟수에 의존하지 않는다.

#### M2-09 · 사전 안의 오타 후보 탐색

- **선행:** M2-05, M2-07, M2-08. **결과:** 한영/자모 후보를 실제 카탈로그 어휘로 제한한다.
- **먼저 작성(U):** `맨투먼`, `후드티이`, `셔트`, `니트으`의 후보 포함 여부, 멀리 떨어진 단어는 후보 없음, 동일 후보 중복 제거.
- **범위/완료:** 후보 개수·입력 길이·거리 상한을 둔 작은 탐색. 후보 포함이 실제 제안 정확도 향상을 보장한다고 표현하지 않는다.

#### M2-10 · 제안 순서와 제안하지 않는 기준

- **선행:** M2-09. **결과:** 같은 입력에 항상 같은 top1을 내고 근거가 약하면 제안하지 않는다.
- **먼저 작성(U):** 점수 동점의 결정적 정렬, 임계값 양쪽, 원문과 동일 후보 제외, 정상 입력/미보유 카테고리 과교정 방지.
- **범위/완료:** 고정 점수식·임계값·최대 제안 수와 버전. 점수를 보정된 확률처럼 표시하지 않는다. 조정은 개발 데이터에서만 한다.

#### M2-11 · 원문 결과에 오타 제안 첨부

- **선행:** M2-10, M2-04. **결과:** 최초 검색은 원문으로 실행하고 후보만 suggestions 배열에 추가한다.
- **먼저 작성(W/I):** 오타 입력의 실행 질의/결과가 원문 검색과 같고, 후보 선택 전 별도 검색이 발생하지 않음. 브랜드·SKU·별칭 정상 입력은 무제안.
- **범위/완료:** 세 모드에 같은 제안 정책을 적용한다. M1 대비 제안 정책이 바뀐 config_version을 기록하고 비교 시 baseline도 새 정책으로 재측정한다. 원문 retrieval과 제안 지표를 구분한다.

### 랭킹과 모드별 불변 조건

#### M2-12 · ranking_v1 고정 가중치

- **선행:** M2-04, M2-11. **결과:** query_v1의 후보 질의에 상품명·브랜드·속성의 고정 필드 가중치만 달리 적용한다.
- **먼저 작성(I):** 통제 fixture에서 가중치가 의도한 순위를 바꾸는지, 같은 어휘·필터·정규화가 유지되는지 확인한다. 실제 개발 점수 개선을 테스트 기대값으로 강제하지 않는다.
- **범위/완료:** 가중치 파일·버전·초기 선택 근거. 가짜 판매량·클릭 점수는 추가하지 않는다. mode 허용과 응답 설정 버전을 연결한다.

#### M2-13 · 세 모드의 공통 계약 회귀

- **선행:** M2-12. **결과:** 모든 모드에서 보호 입력·필터·원문·페이지·오류·인덱스 계약이 같음을 검증한다.
- **먼저 작성(I/W):** 기존 경계 fixture를 모드별로 실행하고 공통 조건을 비교한다. 정상 브랜드/SKU, 없는 색상, 최대 1,000원, timeout 포함.
- **범위/완료:** 버전 문자열뿐 아니라 실제 설정·인덱스 출처를 비교한다. 결과 순위가 달라질 수 있는 부분과 반드시 같아야 할 계약을 구별한다.

### 검색·비교 화면

#### M2-14 · 검색 입력과 결과 표시

- **선행:** M2-11. **결과:** 서버 제공 HTML과 소량의 JavaScript에서 검색어를 보내고 상품 결과를 본다.

- **범위/완료:** 검색 화면 한 개. 초기 접근 가능한 입력 label과 키보드 동작을 확인하고 별도 SPA 도입은 하지 않는다.

#### M2-15 · 화면의 필터와 페이지

- **선행:** M2-14. **결과:** 가격·색상·카테고리와 페이지를 API 조건에 맞춰 조작한다.
- **먼저 준비(B/W):** 필터 후 이동에도 검색 조건 보존, 조건 변경 시 첫 페이지, 마지막 페이지 경계, 잘못된 입력의 필드 오류 표시.
- **범위/완료:** UI가 지원하지 않는 필터 완화를 하지 않는다. 클라이언트 검증과 서버 계약이 일치한다.

#### M2-16 · 로딩·장애·늦은 응답 처리

- **선행:** M2-15. **결과:** 검색 중/0건/입력 오류/503/504를 구분하고 최근 입력의 결과만 표시한다.
- **먼저 준비(B):** 느린 A 요청 뒤 빠른 B 요청, 반복 제출, 네트워크 실패. 늦은 A 결과가 B 화면을 덮어쓰면 실패다.
- **범위/완료:** 요청 취소 또는 최신 요청 식별로 상태를 관리한다. 엔진 장애 화면을 상품 0개로 보여주지 않는다.

#### M2-17 · 제안 명시적 선택

- **선행:** M2-16. **결과:** 사용자가 후보를 선택했을 때만 새 질의로 검색한다.
- **먼저 준비(B/W):** 제안 표시만으로 요청 없음, 클릭 후 선택한 후보 그대로 재검색, 기존 필터 유지/page 초기화, 최초/선택 요청 ID 구분.
- **범위/완료:** 원문과 선택 질의를 화면 상태로 연결한다. `original_query`는 각 HTTP 요청의 q이며 최초 입력을 억지로 응답에 덮어쓰지 않는다. 영구 이벤트 저장은 M4에서 추가한다.

#### M2-18 · 실행 이유 표시

- **선행:** M2-17, M2-01. **결과:** 개발용 표시에서 입력 원문·실행 질의·적용 규칙·시간·설정/인덱스 버전을 확인한다.
- **먼저 준비(W/B):** 별칭 확장, 정상화, 오타 제안이 서로 구별됨. 후보 점수를 확률이나 검색 품질 점수로 표시하지 않음.
- **범위/완료:** 일반 검색 흐름과 개발용 상세 표시를 구분한다. 실행 표현이 실제 질의 계획을 설명하는지 통합 테스트와 대조한다.

#### M2-19 · 세 모드 비교 화면

- **선행:** M2-13, M2-18. **결과:** 같은 입력·필터의 세 모드 결과와 순위·ID·시간을 나란히 확인한다.
- **먼저 준비(B/W):** 세 요청 조건 일치, 서로 다른 인덱스 버전이면 비교 불가 표시, 한 모드 오류를 0건으로 표시하지 않음, 제안 선택 후 결과 별도 구역.
- **범위/완료:** 비교 화면 두 번째 페이지. 브라우저 요청 시간과 서버 시간을 구분하고 이 화면의 동시 요청 시간을 공식 품질 평가 p95와 합치지 않는다.

#### M2-20 · 개발 시드에서 세 모드 실측

- **선행:** M2-19. **결과:** 동일 50개·30개와 인덱스에서 세 모드의 원문/제안 선택 기록을 보존한다.
- **검증(Q/D):** 실제 반환 top1만 선택하며 틀린 후보도 그대로 실행한다. 원문 Hit/MRR, 제안 정확도·커버리지, 정상 오제안, 정답 없음, 지연 비용을 각각 보고한다.
- **범위/완료:** M1 대비 변경된 설정을 공개하고 성공/회귀/개선 없음 사례를 남긴다. 개발셋 결과가 최종 성능이라고 주장하지 않는다.

**M2 완료 게이트:** 세 모드의 실제 I/W, 정상 입력 보호, 자동 재검색 없는 화면, 조건이 같은 실제 비교 파일. 점수 향상 자체를 필수 완료 조건으로 삼지 않는다.

- **범위/완료:** 검색 결과를 보고 정답을 역으로 만들지 않는다. 작성 자료는 튜닝 입력·후보 어휘 소스로 사용하지 않는다.

#### M3-16 · 최종 질의 약 40개 완성

- **선행:** M3-15. **결과:** 약 20개를 더해 총 질의 약 100개 규모를 만든다.
- **검증(S/D):** 그룹 단위 분할을 위해 수량이 달라질 수 있으며 정상/오류/정답 없음 분모는 실제 데이터에서 계산한다.
- **범위/완료:** 개발/최종 분포와 판정 범위 설명. 정확히 60/40에 맞추기 위해 그룹을 나누지 않는다.

#### M3-17 · 사람의 전체 관련성 검토

- **선행:** M3-16 및 실제 사람 검토. **결과:** 확대된 카탈로그 범위에서 판정 근거와 이견 처리를 기록한다.
- **검증(D/S):** 새로운 적합 상품 누락, 속성 경계, 부적합 상품, 정답 없음, 허용 제안을 점검한다. 검토자·일자·범위를 남긴다.
- **범위/완료:** 자동 검사 통과는 사람 검토 대체가 아니다. 피드백 전에는 이 ID와 후속 final 동결을 완료 처리하지 않는다.

#### M3-18 · 데이터·분할·판정 동결

- **선행:** M3-17. **결과:** 개발/최종 집합과 카탈로그의 확정 버전·SHA를 동결한다.
- **검증(S/U):** M3-04 검증기로 정상 자료를 읽고 의도적인 fixture 변조를 거절한다. 실제 동결 파일을 테스트 때문에 바꾸지 않는다.
- **범위/완료:** 동결 이후 개발셋 튜닝과 final 실행이 같은 카탈로그를 사용한다. 변경이 필요하면 기존 결과를 보존한 새 평가 버전을 만든다.

### 개발셋 조정과 최종 실행

#### M3-19 · 확대 snapshot 색인

- **선행:** M3-18, M1-14. **결과:** 동일 분석기/매핑으로 동결 카탈로그를 새 인덱스에 적재하고 검증한다.
- **먼저 확인(I):** 300개 전체 ID/필드/해시, 대표 질의, 실제 인덱스 버전. 동결 카탈로그로 M2-05 후보/보호 어휘도 재생성하고 출처 해시를 설정과 연결한다. 모든 모드가 같은 인덱스와 해당 어휘를 사용한다.
- **범위/완료:** 비교용 별도 실행 설정 또는 아직 없는 별도 alias를 사용한다. M4 교체 기능을 미리 만들거나 기존 읽기 alias를 임의로 덮어쓰지 않는다.

#### M3-20 · 개발셋 한 요소씩 조정

- **선행:** M3-19. **결과:** 개발셋에서 별칭 규칙·제안 임계값·가중치 중 한 요소씩 바꿔 채택 여부를 결정한다.
- **검증(Q/I):** 변경마다 세 모드 비교 조건·설정 버전·정상 회귀·지연 비용을 남긴다. 최대 시도 횟수/중단 기준을 실행 전에 정한다.
- **범위/완료:** 한 조정은 하위 ID로 분리해 TDD/평가한다. final은 실행하거나 실패 분석하지 않는다. 개선이 없으면 기존 설정 유지도 유효한 결론이다.

#### M3-21 · 최종 실행 설정 동결

- **선행:** M3-20. **결과:** 최종 비교에 사용할 각 모드의 설정 파일·해시·코드 상태를 고정한다.
- **검증(D/U):** 분석기·데이터·필터 동일성, 질의/가중치 차이, 제안 정책 동일성, 데이터 동결 기록과 연결.
- **범위/완료:** 실행 전에 조건과 채택 기준을 기록한다. final 결과에 맞춰 같은 버전의 설정을 덮어쓰지 않는다.

#### M3-22 · 최종 평가 실행

- **선행:** M3-21. **결과:** 동결된 final에 대해 세 모드 원문과 제안 선택 지표를 얻는다.
- **검증(Q):** 동결 검증 통과, 실제 선택 집합·분모·정답 없음·제안 커버리지, 세 산출물, 종료 상태와 `valid` 확인.
- **범위/완료:** 결과가 나쁘더라도 보존한다. 계약 오류면 invalid로 보존하고 수정 이유를 공개한다. 결과를 본 뒤 조정했다면 기존 final을 다시 미관측 최종 성적으로 사용하지 않는다.

#### M3-23 · 비교 결과와 실패 사례 보고

- **선행:** M3-22. **결과:** 모드별 변화·정상 입력 회귀·실패 유형·시간 비용을 실행 근거와 연결한다.
- **검증(D/Q):** 개발/최종, 원문/제안 선택, 유효/실패 실행을 구분하고 분모·선택 대상 수·커버리지를 표시한다.
- **범위/완료:** 대표 성공·악화·개선 없음 사례와 채택/기각 이유. 가상 상품·작은 표본·혼자 판정했을 때의 한계를 명시한다.

**M3 완료 게이트:** 확대 데이터/판정 검토, 그룹 격리, 동결 검증, 개발셋 조정 기록, 최종 실행과 보고서. final 지원을 추가했다고 final 평가 완료로 표시하지 않는다.

## 7. M4 — 실패 복구·이벤트·재현 자료

### 색인 교체와 복구

#### M4-01 · Bulk 실패의 재시도 가능 여부

- **선행:** M3-23, M1-13. **결과:** 일시적 실패와 입력/매핑의 영구 실패를 구분한다.
- **먼저 작성(U):** 선택한 ES 버전의 항목 상태/오류 유형별 분류, 모르는 오류는 무한 재시도하지 않음, 성공 ID는 실패 목록에 없음.
- **범위/완료:** 실패 보고서에 분류와 시도 횟수 기록. HTTP 성공 여부만으로 판정하지 않는다.

#### M4-02 · 실패 항목만 제한적으로 재시도

- **선행:** M4-01. **결과:** 재시도 가능한 항목만 정해진 횟수/대기 정책으로 다시 적재한다.
- **먼저 작성(U/I):** 일시 실패 후 성공, 한도 소진, 영구 실패 제외, 성공 항목 재전송 없음, 같은 ID 사용으로 중복 없음.
- **범위/완료:** 실패 ID·원인·최종 상태와 종료 상태를 남긴다. 전송 전체의 결과가 불명확한 경우에도 같은 ID/같은 snapshot으로만 안전하게 재실행한다.

#### M4-03 · 교체 후보의 대표 검색 검증

- **선행:** M4-02, M1-14. **결과:** 데이터 구조뿐 아니라 대표 검색 계약을 만족한 새 인덱스만 교체 후보가 된다.
- **먼저 작성(I):** 정상 브랜드/SKU·필터·0건 대표 질의, 분석기/매핑/해시 불일치, 후보/보호 어휘의 snapshot 불일치. 후보 검증 실패 시 기존 alias가 그대로인지 확인한다.
- **범위/완료:** 검증 대상은 구체적인 후보 인덱스다. 이전/새 인덱스에 해당하는 어휘를 모두 준비해 요청이 확정한 대상에 맞게 선택한다. 아직 연결되지 않은 alias를 검사해서 기존 인덱스를 잘못 통과시키지 않는다.

#### M4-04 · 읽기 alias 원자적 전환

- **선행:** M4-03. **결과:** 검증된 새 인덱스로 alias 대상을 한 번의 원자적 변경으로 바꾼다.
- **먼저 작성(I):** 전환 전/후 각각 단일 대상, 기존 대상이 예상과 다르면 중단, 전환 API 실패 시 상태 재확인.
- **범위/완료:** 이전/새 인덱스·검증 보고서·전환 시각 기록. 병렬 교체를 허용하지 않는 단일 운영 명령으로 시작하며 이전 인덱스는 보존한다.

#### M4-05 · 전환 후 앱 경유 확인

- **선행:** M4-04, M1-28. **결과:** 실제 API가 새 인덱스의 결과와 버전을 반환하는지 확인한다.
- **먼저 작성(I/W):** 정상 질의·필터·0건에서도 새 버전과 후보/보호 어휘의 snapshot 확인, 전환 도중 응답의 상품과 index_version 불일치 방지, 앱 캐시/설정의 옛 버전 오표시 탐지.
- **범위/완료:** API를 통한 사후 검증 결과와 실패 신호. alias 변경 성공만으로 교체 전체를 완료하지 않는다.

#### M4-06 · 사후 검증 실패 시 복구

- **선행:** M4-05. **결과:** 전환 뒤 검증이 실패하면 이전 인덱스로 alias를 복구하고 API를 재확인한다.
- **먼저 작성(I):** 새 인덱스 사후 실패 → 이전 대상으로 복귀 → 이전 버전/대표 검색/후보·보호 어휘 정상. 원래 교체 실패와 복구 성공을 각각 기록한다.
- **범위/완료:** 복구 도중 추가 실패나 이전 인덱스 부재는 명시적인 복구 실패다. 실제 상태를 조회할 수 없는 상황을 복구 성공으로 보고하지 않으며 수동 확인 절차를 제공한다.

#### M4-07 · 상품 수정·삭제 반영 시연

- **선행:** M4-06. **결과:** 가격 수정·상품 삭제·비활성화가 다음 snapshot의 재색인/전환 후 반영된다.
- **먼저 작성(I):** 옛 인덱스는 기존 내용, 새 인덱스는 수정/삭제 내용, rollback 후 옛 내용 복원.
- **범위/완료:** 동결 평가 원본을 건드리지 않는 운영 시연용 별도 snapshot을 쓴다. 실시간 동기화나 CDC라고 표현하지 않는다.

### 검색·선택·클릭 이벤트

#### M4-08 · 이벤트와 요청 연결 계약

- **선행:** M2-17, M4-07. **결과:** 검색·제안 선택·상품 클릭이 어떤 요청을 가리키는지 명확해진다.
- **검증(D):** event_id·type·서버 시각·request_id, 선택 전/후 요청 ID, 상품 ID·표시 순위·mode·버전의 필수/선택 항목과 예시를 정한다.
- **실패 정책:** 서버 검색 로그 저장 실패는 검색 응답을 유지하고 진단으로 남긴다. 이벤트 POST는 실제 저장에 실패하면 실패 응답을 반환한다. UI의 검색/선택은 유지하되 기록 실패를 구별하며 무한 재전송하지 않는다.
- **범위/완료:** 검색은 서버가 기록하고 선택/클릭은 `POST /api/events`로 받는 최소 계약. 인증된 사용자 추적·구매 전환·정확히 한 번 전달 보장은 범위에 넣지 않는다. 중복/클라이언트 보고의 한계를 적는다.

#### M4-09 · 로컬 JSONL 이벤트 저장

- **선행:** M4-08. **결과:** 유효 이벤트 하나를 파싱 가능한 JSON 한 줄로 저장한다.
- **먼저 작성(U):** 한글/줄바꿈 escape, 여러 이벤트 append, 동시 쓰기 시 줄 섞임 방지, 파일 경로/쓰기 실패.
- **범위/완료:** `.gitignore`로 제외되는 `runtime/` 아래 저장 경로와 용량/보관 정책을 명시한다. JSONL 로그와 자유 입력은 Git에 포함하지 않으며 제외 규칙을 확인한다. 파일 저장을 분산 로그 저장소처럼 확장하지 않는다.

#### M4-10 · 검색 요청 이벤트 기록

- **선행:** M4-09, M1-28. **결과:** 검색 응답 request_id로 입력·모드·필터·버전·결과 수·오류를 추적한다.
- **먼저 작성(W/U):** 성공/0건/503/504의 서로 다른 상태, 서버 검색 기록 중복 없음, 요청 원문 보존. 저장 오류가 나도 검색 응답을 유지하고 진단을 남기는 정책을 이 단위에서 구현한다.
- **범위/완료:** 요청 단위 로그를 연결한다. 평가 요청도 기록되면 실제 사용자 행동과 구별할 수 있게 실행 환경/출처를 남긴다.

#### M4-11 · 제안 선택·클릭 이벤트 수신

- **선행:** M4-09. **결과:** `POST /api/events`가 계약에 맞는 사용자 동작만 저장한다.
- **먼저 작성(W):** 모르는 event type, 누락 ID, 잘못된 순위/상품 필드, 과도한 본문 거절; 정상 이벤트의 저장 후 성공 상태와 저장 실패 시 명시적 실패 응답.
- **범위/완료:** schema 검증과 명시적 상태 코드. 영구 요청 저장소 없이 연결 진위를 전부 보장한다고 주장하지 않으며 클라이언트 이벤트의 신뢰 범위를 문서화한다.

#### M4-12 · 화면에서 이벤트 연결

- **선행:** M4-10, M4-11, M2-19. **결과:** 제안 선택 전/후 요청과 클릭한 상품·순위가 JSONL에서 연결된다.
- **먼저 준비(B/W):** 후보 표시만으로 선택 이벤트 없음, 사용자가 고른 후보 그대로 기록, 각 모드 패널의 클릭이 해당 요청에 연결됨.
- **범위/완료:** 키보드/마우스 동작을 같은 방식으로 기록한다. 비교 화면의 여러 API 요청을 독립 사용자 검색으로 과장하지 않는다.

#### M4-13 · 이벤트 저장 실패의 전체 흐름 검증

- **선행:** M4-12. **결과:** 이벤트 저장 실패가 검색 결과 의미를 바꾸거나 성공 저장으로 숨겨지지 않는다.
- **먼저 작성(U/W/B):** 서버 검색 로그 실패 시 검색 응답은 유지하되 진단을 남김; 이벤트 POST 저장 실패는 실패 응답; UI 선택/검색은 유지하고 기록 실패를 구별.
- **범위/완료:** M4-08에서 정하고 각 연결 단위에서 구현한 정책의 통합 회귀 확인. 이미 충족하면 불필요한 구현을 추가하지 않는다. 로그만으로 실제 클릭률/매출 개선을 주장하지 않는다.

#### M4-14 · 별도 부하 시험 조건 확정

#### M4-15 · 반복 요청 측정 실행 경로

- **선행:** M4-14. **결과:** 정해진 조건의 성공/실패 표본과 지연시간을 재현 가능하게 수집한다.

#### M4-16 · 같은 조건의 모드별 시간 측정

- **선행:** M4-15. **결과:** 세 모드의 성공률·시간 분포·요청 수를 같은 조건에서 얻는다.

- **범위/완료:** 작은 데이터의 관찰 결과와 병목 후보를 보고한다. 측정 뒤 최적화가 필요하면 별도 TDD 작업으로 만들고 개발셋으로 품질 회귀를 확인한다. 기존 final 성적은 M3-21의 코드/설정에 귀속된다.

#### M4-17 · 실패와 복구 시나리오 시연

- **선행:** M4-06, M4-13, M4-16. **결과:** 장애 시 어떤 상태·응답·복구 결과가 남는지 재현한다.

#### M4-18 · 새 실행 환경에서 문서 재현

- **선행:** M4-17. **결과:** 문서만 보고 기동·적재·검색·평가·교체·복구를 다시 실행할 수 있다.

#### M4-19 · 결과와 발표용 설명 구성

- **선행:** M4-18. **결과:** 검색 흐름·인덱스 선택 근거·비교표·대표 실패·복구 증거를 설명할 수 있다.
- **검증(D):** 수치마다 원본 세 파일과 실행 조건을 연결하고 가상 데이터/표본/사람 판정의 한계를 표시한다. 검색 개선이 없는 항목도 기록한다.

- **선행:** M4-19. **결과:** 완료 기능·실제 검증·미완료 제약·후속 실험을 정확히 구분한 인계 기록이 남는다.

## 8. 예정 산출물과 수정 위치

아래 경로 중 현재 없는 것은 제안이다. 작업이 필요해질 때 파일을 만들고 이름을 확정한다. 계획에 있다는 이유로 빈 패키지·추상 인터페이스·설정 파일을 한꺼번에 생성하지 않는다.

| 영역 | 예정 위치 | 주로 변경하는 단계 |
|---|---|---|
| 실행 환경 | 루트 Compose, ES/App Dockerfile, 환경 예시, `build.gradle.kts` | M1 |
| 제품 코드 | `src/main/java/org/letter33/commercesearchlab/` 아래 catalog/index/search/query/web 영역 | M1~M2 |
| 불변 검색 설정 | `src/main/resources/search/` 아래 분석기·매핑·별칭·가중치 버전 파일 | M1~M3 |
| 화면 | `src/main/resources/static/` 아래 검색·비교 HTML/JS/CSS | M2 |
| 동작/통합 테스트 | `src/test/java/org/letter33/commercesearchlab/`, 작은 fixture는 `src/test/resources/` | 모든 코드 변경 |
| 기존 평가 도구 | 현재 `src/test/.../evaluation/` | M3 split/동결 확장, M4 별도 시간 측정 |
| 확대 snapshot | 예정 `docs/datasets/` 아래 버전별 상품·질의·판정·동결 manifest | M3 |
| 보존 실행 결과 | 예정 `docs/results/<실험 ID>/`의 manifest/runs/summary와 설명 | M1 이후 |
| 운영 기록 | Git에서 제외할 로컬 JSONL·색인 작업 보고서 경로 | M4 |
| 계약과 실행 안내 | 현재 evaluation-contract/harness/README/worklog와 필요한 운영 안내 | 해당 동작과 같은 단위 |

모든 제품 클래스는 기본 패키지를 유지한다. 테스트용 평가/부하 도구는 제품 JAR에 넣지 않는다. `build/`의 테스트·평가 산출물은 임시이며 보존할 실측 파일은 실행 조건과 함께 따로 저장한다. 실패 실행도 필요하면 별도 폴더로 보존하고 성공 결과를 덮어쓰지 않는다. Git에 보존할 manifest/runs/summary는 질의 원문·오류·접속 정보 등에 민감정보가 없는지 먼저 검토한다. `docs/results/**/runs.jsonl`의 제외 예외는 내용 검토를 생략하는 허용이 아니며, 민감한 원본은 로컬에 보관하고 공개용 사본의 삭제/치환 내역과 측정 한계를 명시한다.

## 10. 첫 구현 요청에서 진행할 순서

첫 활성 작업은 **M1-01 · 버전 조합과 실행 계약 확정**이다. 기존 작업 기록의 넓은 “M1-01 실행 환경 고정”을 이 계획에서 M1-01~M1-04로 세분화했다.

1. 기존 변경과 staged 상태를 확인하고 보존한다.
2. Git 전달 스킬로 M1-01 이슈와 기존 PR을 조회하고 이슈가 없으면 등록한다. 작업 기록에 실제 이슈 URL을 연결한다.
3. JDK/Wrapper/Docker/Compose와 현재 의존성을 확인한다.
4. ES/Nori/공식 Client의 공식 근거를 확인하고 후보 조합을 정한다.
5. 검증할 버전·플러그인·연결·상태 조건을 문서화한다.
6. M1-01 결과/제약과 이슈/PR 상태를 기록하고 M1-02 엔진 기동으로 이어간다. 전달은 해당 이슈의 PR 하나로 진행하며 실제 머지 후 이슈를 종료한다.

요청이 “계획부터”인 현재 작업에서는 구현을 시작하지 않는다. 향후 전체 M1 구현을 요청받으면 M1-01~M1-33의 분할 ID를 포함한 36개 작업을 단위별로 검증하며 순차 진행하고, 환경만 요청받으면 M1-01~M1-04 범위에서 마무리한다.
