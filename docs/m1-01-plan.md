# M1-01 세부계획 · 버전 조합과 실행 계약 확정

작성일: 2026-09-25. 상태: **M1-01 버전·실행 계약과 문서 검증 완료, 실제 엔진 기동은 M1-02에서 진행**.

실제 작업: [이슈 #3](https://github.com/letter333/commerce-search-lab/issues/3), 브랜치 `codex/issue-3-search-engine-contract`. 결과는 [검색 엔진 실행 계약](search-engine-setup.md)에 기록한다. 아래 순서는 계획 이력이며 완료 상태는 문서 마지막 체크리스트와 작업 기록으로 확인한다.

목표는 기존 Java/Spring Boot/Gradle을 유지하면서 사용할 Elasticsearch·Nori·공식 Java Client의 정확한 버전과 로컬 실행 조건을 결정하는 것이다. 결과물은 다음 작업에서 그대로 구현하고 검사할 수 있는 실행 계약이다. 버전 선정의 공식 근거와 실제 엔진·클라이언트 검증 결과를 구분한다.

[전체 구현 계획](implementation-plan.md#4-m1--기본-검색을-실제로-실행하기), [작업 기록](worklog.md), [하네스의 적용 범위](harness.md#적용-범위)를 함께 따른다.

## 2. 작은 실행 순서

H0 PR #2가 머지됐으면 이슈 #1의 종료를 확인하고 최신 `main`에서 분기한다. 아직 미머지여도 문서 조사와 계획 검토는 가능하다. 실제 M1 작업을 먼저 진행할 때는 H0 브랜치의 확인된 SHA에서 별도 분기하고, M1 PR의 base를 H0 브랜치로 명시해 차이를 분리한다. H0 머지 후에는 기준선을 확인하고 M1 PR의 base를 `main`으로 정리한다. squash 등으로 커밋 관계가 달라졌다면 diff를 먼저 확인하고 단순 전달 지시를 이력 재작성 권한으로 해석하지 않는다. 이 계획 작성만으로 H0 머지나 원격 작업을 실행하지 않는다.

## 3. 버전 선정표에 반드시 담을 내용

| 항목 | 기록할 내용 | 판단 기준 |
|---|---|---|
| Elasticsearch | 정확한 버전, 공식 이미지 태그, 플랫폼, 공식 배포/지원 근거 | 로컬 Linux 엔진에서 사용할 수 있는 실제 배포. 부동 태그 금지 |
| Nori | `analysis-nori`, 대상 엔진 버전, 설치 방식·재기동 조건 | 선택한 엔진과 맞는 플러그인 설치·업그레이드 절차 |
| Java API Client | `co.elastic.clients:elasticsearch-java`의 정확한 버전, 공식 호환 범위 | 클라이언트→서버 호환 방향과 제한을 명시. 버전 숫자가 비슷하다는 이유로 통과시키지 않음 |
| 전송 계층 | 후보 버전이 사용하는 HTTP 클라이언트와 TLS·인증 연결 방식 | 실제 사용할 전송 구현을 특정하고 중복/불필요한 전송 의존성 배제 |
| JSON mapper | 후보가 사용하는 Jackson/JSON-P 계열, 패키지·버전·mapper 종류 | 현재 테스트의 `tools.jackson`과 후보의 사용 패키지를 구분. 자동 호환으로 가정하지 않음 |
| Spring Boot 관리 | 현재 BOM이 관리하는 관련 의존성과 후보 POM의 요구 | Boot/JDK/Wrapper는 유지. 충돌 해소가 필요한 이유와 영향 범위 기록 |
| 선정 결과 | 채택 조합·선택 이유·미채택 이유·공식 URL·확인일 | 문서상 근거와 M1-03 실제 연결 증거를 별도 칸으로 관리 |

현재 의존성 확인에는 IntelliJ의 Gradle 실행 기능 또는 저장소 Wrapper의 `dependencies --configuration runtimeClasspath`, `dependencies --configuration testRuntimeClasspath`, `dependencyInsight --dependency jackson-databind --configuration testRuntimeClasspath`를 사용할 수 있다. 현재 빌드에 없는 후보 Client가 조회되지 않는 것은 호환성 검증 결과가 아니다. 후보 POM 조사와 실제 프로젝트 적용 후의 resolved dependency graph 확인을 구분하며, 후자는 M1-03에서 수행한다.

적합한 조합의 근거가 부족하면 부족한 항목을 기록하고 후보를 다시 비교한다. 이 단계에서 기존 스택을 임의 업그레이드하거나 호환성이 검증됐다고 선언하지 않는다.

공식 자료에서 확인한 다음 조건을 후보 비교에 반영한다. 자료 확인일은 2026-09-25이며 실제 선정 시 선택한 버전에 적용되는 설명을 다시 대조한다.

- Java Client의 major/minor 릴리스와 patch 배포 정책을 구분하고, 낮은 minor 클라이언트의 전방 호환과 새로운 서버 API 사용 가능성을 혼동하지 않는다. 서버·클라이언트 각각의 정확한 버전을 기록한다. [Java Client 호환성 정책](https://www.elastic.co/docs/reference/elasticsearch/clients/java)
- Nori는 대상 노드에 설치하고 재시작해야 한다. 선택한 엔진 이미지 안에서 공식 installer가 맞는 플러그인을 설치하도록 설계하며, M1-02의 설치 확인과 M1-09의 실제 분석 토큰 검증을 구분한다. [Nori 설치](https://www.elastic.co/docs/reference/elasticsearch/plugins/analysis-nori), [플러그인 설치와 버전](https://www.elastic.co/docs/reference/elasticsearch/plugins/installing-multiple-plugins)
- 현재 Boot 문서는 Jackson 3를 기본으로 설명하고, Elastic에는 Jackson 2/3용 mapper가 구분되어 있다. `tools.jackson`을 쓰는 평가 테스트와 제품 runtime을 따로 확인하고, 선택한 Client 버전에서 사용할 mapper가 제공되는지 확인한다. [Spring Boot JSON](https://docs.spring.io/spring-boot/reference/features/json.html), [Elastic JSON mapper](https://www.elastic.co/docs/reference/elasticsearch/clients/java/transport)
- 현재 Client 설치 문서의 기본 전송은 HttpClient 5 기반이며 구형 전송은 별도 의존성으로 다뤄진다. 선택 버전의 전송 계층, `jakarta.json`/`javax.json` 차이와 BOM이 선택하는 버전을 확인하고 근거 없이 override하지 않는다. [Client 설치와 의존성](https://www.elastic.co/docs/reference/elasticsearch/clients/java/setup/installation)
- Docker 가이드의 메모리·연결 조건과 선택 버전의 Linux/WSL2 요구를 확인한다. Docker에 할당한 전체 메모리와 단일 ES 컨테이너의 제한을 구분하며, 필요한 커널 설정 변경은 요구 근거·영향을 먼저 기록한다. [Docker 단일 노드 설치](https://www.elastic.co/docs/deploy-manage/deploy/self-managed/install-elasticsearch-docker-basic)
- 단일 노드에서 replica 미할당으로 생기는 `yellow`와 primary shard 장애인 `red`를 구분해 상태 판정 기준을 정한다. [클러스터 red/yellow 진단](https://www.elastic.co/docs/troubleshoot/elasticsearch/red-yellow-cluster-status)

## 4. 로컬 실행 계약에서 결정할 항목

| 항목 | 기본 방향 | M1-01에서 확정할 값·조건 |
|---|---|---|
| 노드·플랫폼 | 개발용 단일 Linux 노드 | 서비스/노드 이름, 플랫폼, 단일 노드 설정 |
| HTTP 접속 | 호스트 loopback에만 공개 | `127.0.0.1` 바인딩, 호스트 포트 후보 `9200`, 컨테이너 포트, 접속 scheme. 포트 충돌 시 다른 프로세스를 종료하지 않고 대체 포트 기록 |
| 노드 간 통신 | 외부 노드 연결 없음 | transport 포트의 호스트 공개 필요 여부. 단일 노드 실험에서는 공개하지 않는 방향 |
| 인증·TLS | 선택한 버전의 기본 보안 동작을 먼저 확인 | 유지할 인증/TLS 방식, CA 신뢰 경로, 앱·점검 도구 접속 방법. 실험 편의 때문에 인증 검증을 무조건 끄지 않음 |
| 비밀값 | 실행 환경에서 주입 | 변수 이름·필수 여부, 실제 `.env` 제외, 루트 `.env.example`에는 빈 값/placeholder만 허용. 실제 토큰·비밀번호·인증서 개인키 기록 금지 |
| 메모리 | 로컬 자원 범위의 재현 가능한 제한 | 컨테이너 메모리 상한, 힙 자동 산정 사용 여부/명시적 힙, 선정 이유. 실제 기동 가능성은 M1-02에서 확인 |
| 데이터 | 개발용 전용 저장 영역 | 볼륨 이름, 재시작 시 유지 범위, 일반 중지와 데이터 초기화 절차 분리. 기존 볼륨 삭제를 정상 종료 절차에 포함하지 않음 |
| 기동·종료 | Compose 기반 | 예정 파일 위치·서비스명·시작/상태/중지 명령, 준비 대기 시간과 실패 시 진단 순서 |
| 상태 판정 | HTTP 응답과 서비스 준비를 구분 | 기대 node 수, health 상태, timeout 기준. 단일 노드의 replica 미할당과 primary 장애를 구분 |

표의 기본 방향은 계획안이다. M1-01 결과물에는 선택한 버전에 맞는 실제 설정 이름·값과 명령을 채운다. 메모리·시간 제한 등 아직 정하지 않은 수치를 현재의 검증 결과처럼 적지 않는다.

## 5. 먼저 설계할 검증 사례

M1-01에서는 아래 검증 절차와 기대값을 문서로 확정한다. **실행 결과 칸은 후속 작업에서 실제 실행 후 채운다.**

| 사례 | 확인 방법 | 기대 결과·실패 처리 | 실제 실행 단계 |
|---|---|---|---|
| Compose 구성이 유효함 | 선택한 파일의 Compose 구성 검사 | 설정 오류·누락 변수는 기동 전에 식별. 변수 값이 펼쳐지는 전체 출력은 증거로 저장하지 않음 | M1-02 |
| 엔진이 응답함 | 선택한 인증/TLS 설정으로 `GET /` | 제한 시간 내 정상 응답. 연결 거부·401/403·TLS 오류·timeout을 각각 실패로 기록 | M1-02 |
| 엔진 버전이 일치함 | `GET /`의 버전 정보 비교 | 선정한 정확한 버전과 일치. 다르면 다른 컨테이너/설정 사용 여부부터 조사 | M1-02 |
| Nori가 설치됨 | 노드 플러그인 정보 조회 | 모든 대상 노드에서 `analysis-nori`와 엔진에 맞는 버전 확인. 누락 시 실패 | M1-02 |
| 단일 노드가 준비됨 | cluster health와 shard 상태 확인 | 예상 노드 수·준비 상태·timeout 조건 충족. `red`나 timeout은 실패. `yellow`를 허용한다면 replica 미할당만인지 근거 확인 | M1-02 |
| 재기동해도 계약이 유지됨 | 같은 구성으로 중지·시작 후 버전·플러그인·health 재조회 | 고정 버전과 Nori 설치가 유지됨. 기존 개발 데이터의 불필요한 삭제 없음 | M1-02 |
| 실제 Client가 엔진에 연결됨 | 제품 설정을 사용하는 엔진 정보 조회 테스트 | 선택 버전의 실제 전송/JSON 경로로 응답 파싱 | M1-03 |
| 잘못된 설정이 드러남 | 누락/잘못된 접속 설정에 대한 테스트 선행 | 구분 가능한 설정·연결 오류. 정상 0건 검색으로 대체하지 않음 | M1-03 |
| 엔진 없이 기존 검증이 가능함 | 엔진 비연결 상태의 기존 `check` | 기존 테스트 통과. 실제 ES 검증은 별도 태스크로 실행하며 미실행을 통과로 처리하지 않음 | M1-03 |
| 테스트 데이터가 격리됨 | 서로 다른 테스트 인덱스의 저장·조회·정리 | 한 테스트의 정리가 다른 인덱스에 영향을 주지 않음 | M1-04 |

M1-01은 문서·환경 계약 작업이므로 형식적인 실패 테스트를 만들지 않는다. M1-02는 구성 전에 점검 명령과 기대값을 준비하고 실제 기동으로 확인한다. M1-03에서 제품 설정·클라이언트 동작을 추가할 때는 테스트 → 의도한 실패 → 최소 구현 → 통과 순서를 적용한다. 환경·의존성 오류만으로 동작의 Red가 확인됐다고 하지 않는다.
